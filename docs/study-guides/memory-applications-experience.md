# Memory, applications and experience: how the system learns and recalls facts

_A study guide._ It covers where facts about the subject are kept, how a document, an answer given at a form, a finished design run and a studio record each become stored facts, how a form page recalls them, and how to correct and measure them. Line numbers are as of commit `7441369b`. Every example uses made-up companies: Company A, Company B and Acme.

> **Policy values change.** `packages/browser-session/config/answering/standard.json` `"drafts"` decides what happens to a drafted suggestion by its basis: `fill` types it into the form without the operator seeing it, `offer` sends it to the operator as a lettered choice. Read the file for the current values before you rely on either (§4, §5, §13). A typed draft is never taught into the record.

## 0. How to read this guide

The guide answers five questions.

1. **Where do facts live?** One Qdrant collection holds every memory point. Postgres holds the records around it. Files hold run dumps, session dumps and the ingest manifest. See §2.
2. **How does a document become facts?** `memory-ingest` cuts it into chunks and posts each chunk to the `document-memory` orchestration. That orchestration digests the chunk with a model pipeline and stores what the digest endorses. See §3.
3. **How does an answer given during an application become a fact?** The browser session caches the answer for the open unit of work, then teaches it at once as a one-section `guidance` document through the same orchestration. See §4.
4. **How does a form page get its evidence?** The `form-memory` orchestration searches the store with each field's own question, with no model call. It then runs the `field-answer` pipeline over what it found, and a declared table routes each field. See §5 and §6.
5. **How do applications, design lessons and the studio fit?** An application is a unit of work, and its key scopes the memories recorded in it (§7). Design lessons are a separate kind that only the design coach reads (§8). Studio experiences reach memory only through an exported document (§9).

Then: removing and correcting facts (§10), measuring and observing (§11), four worked examples (§12), and every knob in one table (§13).

## 1. Vocabulary

- **Subject.** The person the facts are about. A document names it in its head. A browser session takes it from `packages/browser-session/src/config.ts:100` `BROWSER_SESSION_SUBJECT`, whose fallback is the placeholder `the subject`.
- **Memory point.** One stored memory: one Qdrant point with two named vectors and a payload (`packages/quality-loop/src/orchestrators/memory/ports.ts:47` `VECTOR_NAMES`). The `condition` vector embeds when the memory applies; the `lesson` vector embeds what it says. The stored text is the insight, then `— applies when`, then the condition (`packages/contracts/src/lib/quality-loop/lessons.ts:21` `lessonText`). The point id is a hash of the run id and the ref (`packages/quality-loop/src/modules/memory/qdrant/collection.ts:104` `pointId`).
- **Kind.** What a point is (`packages/quality-loop/src/pipelines/memory-recall/input.ts:106` `CHUNK_KINDS`). Three families matter here:
  - _lesson_: design advice learned from a finished run (`packages/quality-loop/src/orchestrators/memory/store/chunks.ts:17` `DEFAULT_CHUNK_KIND`);
  - _document kinds_: facts about the subject — `profile_fact` (one thing true of the subject), `profile_story` (a course of events kept whole), `claim_boundary` (a bound on what the subject may claim) (`packages/contracts/src/lib/quality-loop/document-digest.ts:50` `DOCUMENT_MEMORY_KINDS`, meanings at `packages/contracts/src/lib/quality-loop/document-digest.ts:54` `DOCUMENT_MEMORY_KIND_USES`);
  - _knowledge kinds_: engineering knowledge — `fact`, `anti_pattern`, `pattern`, `procedure` (`packages/contracts/src/lib/quality-loop/knowledge.ts:31` `KNOWLEDGE_ITEM_KINDS`).

  Only document kinds are ever evidence for a form.

- **Scope.** Where a memory holds — the units domain's vocabulary, read by the digest, the answerer and every store (`packages/contracts/src/lib/units/scope.ts:12` `MEMORY_SCOPES`). `subject`: true wherever asked. `unit`: true only of the one employer, role or application it was recorded for (`packages/contracts/src/lib/units/scope.ts:16` `MEMORY_SCOPE_USES`). A point with no scope reads as `subject` (`packages/contracts/src/lib/units/scope.ts:23` `DEFAULT_MEMORY_SCOPE`).
- **Unit-bound.** A scope a total table marks as bound to one unit of work (`packages/contracts/src/lib/units/scope.ts:31` `SCOPE_BOUND_TO_UNIT`). Today that is `unit` alone (`packages/contracts/src/lib/units/scope.ts:37` `UNIT_BOUND_SCOPES`; test `packages/contracts/src/lib/units/scope.ts:46` `isUnitBound`). A unit-bound memory carries a unit key and is read only by a search that names the same key.
- **Unit of work.** One piece of work a mission repeats; in the job-site mission, one application (`packages/browser-session/goals/linkedin-easy-apply.md:5` `## Unit of work`). A plan opens one with `taskStart` and closes it with `taskDone` (`packages/browser-session/src/core/step-executor.ts:71` `openTaskUnlessRefused`, `packages/browser-session/src/core/step-executor.ts:155` `closeTask`).
- **Unit key.** The string a unit's memories are filed and searched under (`packages/contracts/src/lib/units/identity.ts:102` `unitKeyOf`): the identity key of the facets the mission declares, or the unit's own id when it carries none. The identity key is `name=value` lines sorted by name (`packages/contracts/src/lib/units/identity.ts:56` `identityKey`), each value trimmed, NFKC-normalised and lower-cased (`packages/contracts/src/lib/units/identity.ts:49` `facetKey`). At Acme, the job-site mission's key is `company=acme`.
- **Run.** One quality-loop pipeline run: a producer, validators, critics, evaluators and a deterministic controller, recorded in `quality_run` (`packages/db/src/entities/quality-run.entity.ts:80` `QualityRun`) and dumped under `static/runs`.
- **Orchestration.** A declared chain of steps over runs, recorded in `orchestration_run` (`packages/db/src/entities/orchestration-run.entity.ts:35` `OrchestrationRun`) and run by `packages/quality-loop/src/orchestrators/runner/run-orchestration.ts:203` `runOrchestration`. Three orchestrations write memory (`memory`, `document-memory`, `knowledge`); `form-memory` only reads it.
- **Digest.** A run that turns a document chunk (`packages/quality-loop/src/pipelines/document-digest/definition.ts:37` `DOCUMENT_DIGEST`) or a finished run (`packages/quality-loop/src/pipelines/experience-digest/definition.ts:25` `EXPERIENCE_DIGEST`) into proposed memories, each citing what it came from.
- **Recall.** A search of the store for one ask. Form recall uses the fields' own words and no model (`packages/quality-loop/src/orchestrators/form-memory/steps.ts:103` `recall`). Design recall derives probes with a model and has a curator pipeline pick the useful hits (`packages/quality-loop/src/orchestrators/memory/recall/recall-memory.ts:118` `recallMemory`).
- **Evidence item.** One recalled memory as a form goal lists it, under an alias `m1`, `m2`… (`packages/contracts/src/lib/browser-session/field-goal.ts:241` `evidenceItemSchema`; rendered by `packages/contracts/src/lib/browser-session/field-goal.ts:342` `evidenceLine` as `- [m1] kind · scope — text · stored when · origin ref`, where `origin` is the program that wrote it — a pipeline's id — and `ref` its address there, `<runId>#<ref>`; read back by `packages/contracts/src/lib/browser-session/field-goal.ts:469` `readEvidenceItems`, the line's exact inverse).
- **Withholding.** A declared rule that keeps a located part of a run's artifact (a memory `memory.N`, a field `field.N`) from being used, because a confirmed finding or a validator problem names it (`packages/quality-loop/src/core/outputs/withheld.ts:149` `withheldItems`; rules read from the pipeline by `packages/quality-loop/src/core/outputs/withheld.ts:69` `withholdingOf`). Each finding type declares `every-ref`, `every-ref-when-requires-user` or `none`.
- **Admission.** The verdict on whether a run's artifact may be drawn on at all (`packages/quality-loop/src/core/outputs/run-outputs.ts:61` `admission`): `admitted`, `fell-short`, `no-rubric` or `no-artifact`. It deliberately ignores the `policyAllowed` gate.

```text
├── vector "condition"  <- embed(appliesWhen)   "a form asks whether the subject needs sponsorship"
```

**Boot, in four steps.**

1. `packages/llm/src/create-client.ts:165` `createEmbeddingClientFromEnv` builds the embedding client. With no `OPENAI_API_KEY` it is a `packages/llm/src/embedding-client.ts:26` `DisabledEmbeddingClient` with no model, and nothing is recalled or learned.
2. `packages/quality-loop/src/modules/memory/memory.module.ts:46` `qdrantStore` binds the store to that model and width.
3. `packages/quality-loop/src/modules/memory/memory.service.ts:89` `onModuleInit` calls `packages/quality-loop/src/modules/memory/qdrant/qdrant-memory-store.ts:83` `verify`, which creates the collection if needed, asks for every payload index, counts the points, and returns all of that as data. `onModuleInit` then logs `memory store ready: <collection> (<n> chunks)`, or `memory store not ready: <reason>`.
4. Each memory orchestration snapshots `{embedding, store: verify()}` when it opens (`packages/quality-loop/src/orchestrators/document-memory/definition.ts:50` `context`; shape `packages/contracts/src/lib/quality-loop/memory.ts:71` `memoryContextSchema`). Later steps read that snapshot, not the live store.

**How a search states what it wants.** A probe carries a `packages/quality-loop/src/orchestrators/memory/ports.ts:133` `ProbeFilter` of `kinds`, `pipelines`, `notRunIds` and `unitKey`. `packages/quality-loop/src/modules/memory/qdrant/qdrant-memory-store.ts:57` `filterOf` turns it into Qdrant `must` and `must_not` clauses. Form recall narrows to the document kinds and the page's unit (`packages/quality-loop/src/orchestrators/form-memory/probes.ts:66` `formEvidenceFilter`). The knowledge probes narrow to knowledge items and lessons (`packages/quality-loop/src/orchestrators/knowledge/known/probes.ts:123` `knownFilter`). Design recall and the retrieval report set no filter (`packages/quality-loop/src/orchestrators/memory/recall/query.ts:103` `probesOf`). Every search, with a filter or without, leaves out unit-bound memories of other units (§6).

**Gotchas.**

1. **A new embedding model points at a new, empty collection.** The name carries the model and width. Change `OPENAI_EMBEDDING_MODEL` and `verify` reports a fresh collection with 0 chunks; recall then skips as `store-empty` while the old points sit in the old collection. Re-index rebuilds design lessons only (`packages/quality-loop/src/modules/memory/memory.service.ts:109` `reindex`). Documents must be ingested again.
2. **Replacing a run's points is a delete, then an upsert, in two calls** (`packages/quality-loop/src/modules/memory/qdrant/qdrant-memory-store.ts:131` `replaceRunChunks`). If the upsert fails after the delete, the run's points are gone and the step fails as `store-unavailable` (`packages/quality-loop/src/orchestrators/memory/store/index-memories.ts:85` `indexMemories`). A process that dies between the two calls reports nothing.
3. **A point whose payload does not parse is invisible.** `fromPayload` is strict, through the strict source schema (`packages/quality-loop/src/pipelines/memory-recall/input.ts:123` `chunkSourceSchema`). Every search skips such a point, but it still counts in `verify().chunks`, still takes over-fetch slots, and `retractPoint` answers `unreadable` and leaves it standing. Two builds that share one collection can hide each other's points.
4. **The embedding cache key leaves out the width**: `memory_embedding` is unique on model and hash (`packages/db/src/entities/memory-embedding.entity.ts:12` `MemoryEmbedding`). This is latent while the width is always 1536 (`packages/llm/src/embedding-client.ts:23` `EMBEDDING_DIMENSIONS`).
5. **Availability is read when an orchestration opens.** Store steps check the snapshot (`packages/quality-loop/src/orchestrators/document-memory/steps.ts:140` `store`), so a store that recovers mid-run still makes the step skip.
6. **`verify().chunks` counts the whole collection**: every writer, every kind, unreadable points too. It is not a count of facts.
7. **A point id names a position, not a fact.** The ref is `memory.<position>`, the proposal's 1-based index (`packages/quality-loop/src/orchestrators/memory/store/chunks.ts:84` `ref`). It is stable across a re-index; a new digest renumbers, so one id can later hold another fact.
8. **The manifest is the only link from a document's path to its digest runs.** The store holds no document path and no chunk hash; `ManifestEntry.digestRunId` names the run the points are filed under. Each `document-memory` orchestration record also names its digest run (the digest step's run ids) beside the document's title, which is the file's basename (`packages/memory-ingest/src/core/ingest.ts:138` `title`), and its chunk (the step's report, `packages/quality-loop/src/orchestrators/document-memory/steps.ts:83` `report`), so the runs can still be found by hand.
9. **A session dump is whole only after the session closes** (`packages/browser-session/src/core/session-dump.ts:212` `closingFiles`). A running or crashed session has `00-rubrics.json` and `01-steps/` only.
10. **About 441 older dump folders cannot be served.** The dump reader admits only `quality`, `session` and `criteria` run ids (`packages/run-dump/src/run-id.ts:17` `RUN_KINDS`), so `GET /runs/:id/dump` answers 404 for the `-prompt`, `-eval`, `-suggestion` and `-improve` folders.

## 3. Flow A — a document becomes facts (ingest)

`memory-ingest` is a command-line tool with no server. It reads a file (PDF, markdown or text, JSON Lines), cuts it into structural parts (headings, list items, paragraphs), packs the parts into chunks, and renders each chunk as one markdown goal. The sha256 of that goal is the chunk's identity. Each goal is posted on its own to the loop's `document-memory` orchestration and awaited. The orchestration runs the `document-digest` pipeline, reads back the memories the run endorses, applies the document's declared scope, and stores what survives under the digest run's id. The tool records each outcome in a JSON manifest. Once every chunk of the document's current plan is covered, it retracts the document's older digest runs: make before break.

```text
person          memory-ingest CLI                      quality loop :3003                   stores
  | ingest notes.md --kind notes --scope subject --date 2026-10-14
  |--------------->| 1 plan: reader -> parts -> pack -> chunks; sha256 of each goal
  |                | 2 take manifest.lock; load manifest.json; skip covered chunks
  |                |-- POST /orchestrations/document-memory {goal, maxIterations: 2} -->|
  |                |                                       | refuse a goal with no document index
  |                |                                       | open: context = {embedding, store.verify()}
  |                |<------------------ 202 {orchestrationRunId} ---|
  |                |-- GET /orchestrations/:id, every 3 s ------------>| step "digest":
  |                |                                       |   child run of document-digest
  |                |                                       |   (criteria, producer, validators,
  |                |                                       |    3 critics, 2 evaluators, controller)
  |                |                                       |   readDocumentDigest: endorse, stamp
  |                |                                       |   scope, stamp unitKey or withhold
  |                |                                       | step "store": indexMemories
  |                |                                       |   embed through the cache --------> memory_embedding
  |                |                                       |   replaceRunChunks(digestRunId) --> Qdrant points
  |                |<----------- settled record (steps.digest, steps.store) ---|
  |                | 3 append a ManifestEntry; save (temp file, then rename)
  |                | 4 every chunk covered? DELETE /memory/<older digestRunId> ----------> Qdrant
  |<-- report -----| exit 0; 1 when anything failed or was left out; 2 on bad usage, unusable input or a held lock
```

**Steps.**

_Plan, with no network._

1. Parse the command line against the per-command flag table (`packages/memory-ingest/src/cli.ts:148` `parseOptions`; flags in `packages/memory-ingest/src/config.ts:77` `INGEST_FLAGS`). `--scope` accepts only scopes that are not unit-bound, which today means `subject` (`packages/memory-ingest/src/config.ts:39` `INGEST_SCOPES`).
2. Take the manifest lock when the command saves the manifest (`packages/memory-ingest/src/cli.ts:56` `savesManifest`; `packages/memory-ingest/src/adapters/fs-ledger/json-file-ledger.ts:187` `lock`). A lock already there ends the run with exit 2 (`packages/memory-ingest/src/adapters/fs-ledger/json-file-ledger.ts:121` `ManifestLocked`).
3. Read and chunk every path before anything is posted (`packages/memory-ingest/src/core/ingest.ts:127` `planIngest`). A document's key is its path relative to the working directory (`packages/memory-ingest/src/core/record.ts:40` `documentKey`).
4. Pick a reader by file extension (`packages/memory-ingest/src/adapters/readers/reader-table.ts:13` `READERS`). Markdown and text are read as they are (`packages/memory-ingest/src/adapters/readers/markdown-reader.ts:6` `markdownReader`). A PDF is read page by page, and lines in larger type become `#` headings (`packages/memory-ingest/src/adapters/readers/pdf-blocks.ts:80` `headingLevels`). JSON Lines become one heading per record (`packages/memory-ingest/src/adapters/readers/jsonl-reader.ts:131` `recordText`).
5. Split the text into parts: headings, list items with their continuation lines, and paragraphs, each with its heading path (`packages/memory-ingest/src/core/chunk.ts:124` `partsOf`). A part over 1,500 characters is cut at the last whitespace before the cap (`packages/memory-ingest/src/core/chunk.ts:156` `splitOversize`).
6. Pack greedily: a part joins the current chunk while the chunk has at most 8 parts and still renders within 6,000 bytes (`packages/memory-ingest/src/core/chunk.ts:219` `pack`; `packages/memory-ingest/src/core/chunk.ts:68` `PARTS_PER_CHUNK`; `packages/memory-ingest/src/config.ts:44` `DEFAULT_CHUNK_BYTES`).
7. Build each chunk, check it against the contract, and hash its goal (`packages/memory-ingest/src/core/chunk.ts:243` `chunkDocument`; `packages/contracts/src/lib/quality-loop/document-digest.ts:101` `documentChunkSchema`; `packages/memory-ingest/src/core/chunk.ts:183` `chunkHash`).
8. Render the goal (`packages/contracts/src/lib/quality-loop/document-digest.ts:203` `renderDocumentGoal`). It holds a head line (`Kind · Subject · Dated · Chunk i of N · Under: <headings>`, from `packages/contracts/src/lib/quality-loop/document-digest.ts:167` `headLine`), one `### [section.N]` per part, `## Rules` (the six document rules, less the scope test when the document declares a scope: `packages/contracts/src/lib/quality-loop/document-digest.ts:189` `rulesOf`), `## Limits`, and a fenced JSON `## Index` that no model is shown (`packages/contracts/src/lib/quality-loop/document-digest.ts:134` `documentIndexSchema`). The validators, the orchestrator's refusal (step 12) and the digest reader (step 17) read it. A goal over 64,000 bytes is refused (`packages/contracts/src/lib/quality-loop/goal-index.ts:36` `withinBudget`).

_Post and wait._

9. Load the manifest and find each chunk's latest posting by document and chunk hash (`packages/memory-ingest/src/core/ingest.ts:240` `runIngest`; `packages/memory-ingest/src/core/ingest.ts:159` `chunkKey`). A chunk whose posting covers it is skipped unless `--force` (`packages/memory-ingest/src/core/record.ts:248` `covers`).
10. Post one chunk as `POST /orchestrations/document-memory` with `{goal, maxIterations: 2}` (`packages/memory-ingest/src/adapters/loop-http/loop-ingest-sink.ts:91` `post`; `packages/loop-client/src/http-loop-client.ts:145` `startOrchestration`). The loop answers 202 with the orchestration id (`packages/quality-loop/src/modules/orchestration/orchestration.controller.ts:28` `start`).
11. Wait: poll `GET /orchestrations/:id` every 3 s, and watch the live child run's heartbeat (`packages/loop-client/src/await-run.ts:89` `awaitOrchestration`; `packages/loop-client/src/await-run.ts:14` `DEFAULT_POLL_EVERY_MS`).

_Admit, in the loop._

12. Refuse a goal that carries no document index, or one that declares a unit-bound scope and names no unit (`packages/quality-loop/src/orchestrators/document-memory/definition.ts:32` `refuseNonDocument`, called from `packages/quality-loop/src/modules/orchestration/orchestration.service.ts:133` `admit`). Both answer 400 before any row exists.
13. Open the record with the store snapshot (`packages/quality-loop/src/modules/orchestration/orchestration.service.ts:147` `open`), then run `digest` and `store` in the background (`packages/quality-loop/src/orchestrators/runner/run-orchestration.ts:203` `runOrchestration`).

_Digest, in the loop._

14. Skip when embeddings are off (`embeddings-disabled`) or the pipeline is not registered; otherwise run `document-digest` as a child run (`packages/quality-loop/src/orchestrators/document-memory/steps.ts:74` `digest`).
15. The pipeline (`packages/quality-loop/src/pipelines/document-digest/definition.ts:37` `DOCUMENT_DIGEST`) derives up to 24 criteria of kinds `fact` and `rule`. The producer writes at most 16 memories, each with a kind, a scope, 1 to 4 cited sections, an insight and an appliesWhen (`packages/quality-loop/src/pipelines/document-digest/output.ts:56` `documentDigestSchema`). Two validators check the aliases and the limits against the index (`packages/quality-loop/src/pipelines/document-digest/validators.ts:73` `referencesValidator`; `packages/quality-loop/src/pipelines/document-digest/validators.ts:80` `limitsValidator`). The critics `grounding`, `coverage` and `usability` look for defects; the evaluators `capture` and `rules` grade the criteria; the controller decides. No model ever sees the index: every prompt's goal has it stripped (`packages/quality-loop/src/core/stages/prompting.ts:65` `goalSection`).
16. What withholds: `invented_fact`, `misread_section` and `misscoped_fact` gate the run and withhold every memory they name; every other finding type withholds nothing (`packages/quality-loop/src/pipelines/document-digest/definition.ts:157` `findingTypes`). When the document declares its scope, `misscoped_fact` withholds nothing either (`packages/quality-loop/src/pipelines/document-digest/definition.ts:185` `WITHHOLDING_UNDER_DECLARED_SCOPE`).
17. Read back what may be stored (`packages/quality-loop/src/orchestrators/document-memory/read-document-digest.ts:48` `readDocumentDigest`, through `packages/quality-loop/src/orchestrators/memory/digest/endorsed.ts:140` `endorsedMemories`). The digest is drawn on when it was `admitted`, or when it `fell-short` with its artifact present and its validators passed (`packages/quality-loop/src/orchestrators/document-memory/steps.ts:57` `DOCUMENT_MEMORY_ADMITS`). A declared scope overwrites every memory's scope. A unit key on the document is stamped on every unit-bound memory; with no key, those memories are withheld as `unit-unnamed` (`packages/quality-loop/src/orchestrators/document-memory/read-document-digest.ts:42` `UNIT_UNNAMED`).
18. The step reports `memories` (proposed), `kept` and `unit-unnamed` counts, and a reason when something was left out: `unit-unnamed`, `not-accepted`, `no-rubric`, `no-artifact` or `no-memories` (`packages/contracts/src/lib/quality-loop/document-memory.ts:23` `DOCUMENT_MEMORY_STEP_REASONS`).

_Store, in the loop._

19. Skip with `store-unavailable` when the snapshot said the store was not ready (`packages/quality-loop/src/orchestrators/document-memory/steps.ts:140` `store`).
20. Build one chunk per memory (`packages/quality-loop/src/orchestrators/memory/store/chunks.ts:66` `chunksOf`): the text, the two keys, the hash, a source with `pipeline: document-digest` and `ref: memory.N`, the lineage (`packages/quality-loop/src/orchestrators/memory/store/index-memories.ts:49` `originOf`), the scope and the unit key. A kind this writer does not own is filed under its first owned kind, `lesson` (`packages/quality-loop/src/orchestrators/memory/store/chunks.ts:49` `chunkKind`), and counted as `retyped`.
21. Embed both texts of every chunk in one batch through the cache (`packages/quality-loop/src/orchestrators/memory/store/index-memories.ts:120` `embed`), then replace the digest run's owned kinds with the new points (`packages/quality-loop/src/orchestrators/memory/store/index-memories.ts:125` `replaceRunChunks`).

_Record and replace, in the CLI._

22. Build the manifest entry (`packages/memory-ingest/src/core/record.ts:213` `entryOf`). `digestRunId` is the digest step's child run. `status` is `failed` when the orchestration did not complete, `complete` when the store step completed, and `unstored` otherwise (`packages/memory-ingest/src/core/record.ts:77` `statusOf`). The manifest is saved after every posting (`packages/memory-ingest/src/adapters/fs-ledger/json-file-ledger.ts:176` `save`).
23. Classify the outcome as `posted`, `no-facts`, `unstored`, `failed`, `refused` or `skipped` (`packages/memory-ingest/src/core/ingest-report.ts:40` `outcomeOf`). Only the reason `no-memories` means "this chunk holds no facts" (`packages/memory-ingest/src/core/record.ts:124` `HOLDS_NO_FACTS`).
24. Make before break. When no chunk of the current plan is pending or uncovered, retract every other digest run of the document (`packages/memory-ingest/src/core/retract.ts:170` `replaceDocument`, using `packages/memory-ingest/src/core/retract.ts:156` `replacedRunsOf`, each through `DELETE /memory/:id`). Otherwise the report names the chunk that held the replacement back, and nothing is retracted.
25. Print the report (`packages/memory-ingest/src/render.ts:135` `renderIngest`) and exit by it (`packages/memory-ingest/src/cli.ts:224` `execute`): 1 on any `failed` or `unstored` chunk (a refused chunk counts as failed), a stop, or runs left standing (`packages/memory-ingest/src/core/retract.ts:60` `leftStanding`); 2 on a usage error (a missing subject included), an input it cannot use, or a held lock; 0 otherwise.

**Data that crosses.**

| From → to                | What                                   | Shape                                                                                                                                                                                    |
| ------------------------ | -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CLI → loop               | the rendered goal and an iteration cap | `{goal, maxIterations: 2}` (`packages/memory-ingest/src/adapters/loop-http/loop-ingest-sink.ts:23` `INGEST_MAX_ITERATIONS`)                                                              |
| digest step → store step | what the digest endorsed               | `MemoryToStore {position, insight, appliesWhen, evidence, iterations, kind?, scope?, unitKey?}` (`packages/quality-loop/src/orchestrators/memory/digest/endorsed.ts:45` `MemoryToStore`) |
| store step → Qdrant      | one point per memory                   | id `pointId(digestRunId, "memory.N")` (`packages/quality-loop/src/modules/memory/qdrant/collection.ts:104` `pointId`)                                                                    |
| loop → CLI               | the settled orchestration              | steps with status, reason, note, counts, run ids (`packages/contracts/src/lib/quality-loop/orchestration.ts:46` `OrchestrationStepDto`)                                                  |
| CLI → disk               | one record per posting                 | `ManifestEntry` (`packages/memory-ingest/src/core/ports.ts:164` `ManifestEntry`)                                                                                                         |

**Gotchas.**

1. **"Every fact was rejected" reads as "this chunk holds no facts".** An admitted digest whose every memory a confirmed false-fact finding withholds still answers `no-memories`; a spec pins it (`packages/quality-loop/src/orchestrators/document-memory/steps.spec.ts:288` `everyMemoryFaulted`). The CLI counts `no-memories` as covered, so the chunk is skipped on later runs, and make before break retracts the older digest that held its facts. The only tell is `steps.digest.counts.memories` greater than `kept`.
2. **A start that times out leaves a run the manifest cannot name.** A POST the loop may have received is never repeated (`packages/loop-client/src/http-loop-client.ts:52` `repeatable`), and a timeout is recorded `failed` with no orchestration id. The run may still digest and store, and the next ingest posts the chunk again, so its facts are stored twice. Find the run with `GET /orchestrations?orchestrator=document-memory` and retract its digest run by hand.
3. **A second Ctrl-C drops the record of the chunk in flight** (`packages/memory-ingest/src/main.ts:17` `bootstrap`). The orchestration still settles and stores; a re-run stores the facts again.
4. **A document's identity hangs on its path, the working directory and the manifest home.** Move or rename the file, or run from elsewhere, and it is a new document whose old facts are never replaced. Run `retract <old path>` from the original directory.
5. **"Chunk i of N" is inside the hash.** Insert one part and every later chunk's goal changes. Change the title, date, scope, subject, kind or rules and every chunk changes. The whole document is then digested again, which costs model calls. Replacement goes by document so that this leaves no duplicates (the comment above `packages/memory-ingest/src/core/ingest.ts:70` `IngestOptions` records 48 old facts once standing beside 50 replacements).
6. **Model calls are spent even when the store is down.** The digest step checks only that embeddings are on; the store step trusts the snapshot. `store-unavailable` does not cover the chunk, so the next run digests it again.
7. **Without `--scope`, one unit-bound memory keeps its chunk uncovered.** A file names no unit, so such memories are withheld as `unit-unnamed`. That reason covers nothing (`packages/memory-ingest/src/core/record.ts:124` `HOLDS_NO_FACTS`), so the chunk is posted and digested again on every run, the run exits 1, and replacement is held back, for as long as each new digest still scopes a memory `unit`. Ingesting with `--scope subject` ends it.
8. **A declared scope still costs a scope finding its gate.** Under `--scope subject`, `misscoped_fact` withholds nothing but still counts against the run, which can then fall short. Its memories are stored anyway, because a `fell-short` digest is drawn on when the engine's own gates held, and the step notes "judged below the bar, not refuted: stored".
9. **A failed child run reads `unstored`, not `failed`.** `runFailed` carries no error (`packages/quality-loop/src/orchestrators/common.ts:117` `runFailed`), so the orchestration settles `complete` and the CLI records `unstored`. A manifest `failed` means an unexpected error or a failure on the client side.
10. **Changing loops with the same manifest posts nothing.** Coverage ignores `loopUrl`. Point `QUALITY_LOOP_URL` at a fresh loop and every chunk is skipped; use `--force` or a separate `MEMORY_INGEST_HOME`.
11. **Dense chunks lose facts silently.** At most 16 memories survive per chunk (`packages/contracts/src/lib/quality-loop/document-digest.ts:29` `DOCUMENT_MAX_MEMORIES`). Facts the producer never wrote leave no trace.
12. **A stale `manifest.lock` blocks every writing command.** A process killed outright leaves it, and it must be deleted by hand.
13. **Near-duplicates are stored.** `duplicate_fact` withholds nothing, and search dedupes only identical text (`packages/quality-loop/src/modules/memory/qdrant/qdrant-memory-store.ts:105` `searchMany`).

## 4. Flow B — an answer given during an application becomes a fact (teach)

When a form needs a value that nothing trusted settles, the session asks the operator. The question goes to the terminal and, through the notifications bus, to Telegram; the first answer wins. Once the page accepts the answer, the session does two things. It caches the answer for the open unit of work, keyed by what the field asks, so the next form of the same unit is filled without asking. And it teaches the answer at once, as a `guidance` document of one section that names the unit in its index, posted to the same `document-memory` orchestration a file goes through (Flow A, steps 12 to 21). The stored point is the fact. The session does not wait for it to be stored.

```text
page              browser session                          operator channels          quality loop
  | form page         |                                          |                          |
  |------------------>| askFields(refs)                          |                          |
  |                   | openOf: drop fields still holding what   |                          |

  |                   | answerFields --> form-memory (Flow C) -------------------------------->|
  |                   | routeFields: some field -> ask-operator   |                          |
```

17. One document per answer (`packages/browser-session/src/core/field-teach.ts:122` `teach`, through `packages/contracts/src/lib/browser-session/guidance.ts:149` `guidanceDocuments` and `packages/contracts/src/lib/browser-session/guidance.ts:119` `guidanceDocument`). It has kind `guidance`, the title `Operator guidance — session <id>`, the unit key in its head when a unit was open, one section, the document rules plus `GUIDANCE_RULE` (`packages/contracts/src/lib/browser-session/guidance.ts:96` `GUIDANCE_RULE`), and room for one memory. The section reads, for example, `Asked "Are you authorized to work here?", offering Yes | No, the subject answered "Yes". Asked on 2026-10-14 in the unit of work "Engineer at Acme".` (`packages/contracts/src/lib/browser-session/guidance.ts:102` `renderGuidanceSection`).
18. Under the `loop` brain (`config/engine.json` `brain`), start the orchestration and return without waiting (`packages/browser-session/src/adapters/loop-http/loop-brain.ts:144` `teach`, through the `BrainPort.teach` the engine calls with the answers, the session and the subject): `POST /orchestrations/document-memory` with two iterations (`packages/browser-session/src/adapters/loop-http/loop-brain.ts` `TEACH_ITERATIONS`); each answer's receipt says `queued` with the orchestration id of its document as its reference. Under the `memory` brain the same call writes each answer to the memory space as one deterministic fact (`packages/browser-session/src/adapters/memory-loop/teach.ts` `rememberAnswers`) and each answer's receipt carries its own record id and the write's outcome — one receipt per answer, so a decision row's `teaching_ref` names exactly the record its answer went to.
19. Link the decision row to the orchestration (`packages/browser-session/src/adapters/mikro-orm/mikro-orm-ledger.ts:191` `recordTeaching`), add the teaching to the step's list and rewrite `01-steps/NN/teach.json`. That list is reset when each step begins (`packages/browser-session/src/core/step-flow.ts:64` `observe`). After the form, `fields.json` holds every field's route and result (`packages/browser-session/src/core/field-flow.ts:336` `dumpFields`).
20. In the loop the guidance document goes through Flow A's steps 12 to 21. It declares no scope, so the digest applies the scope test, and `GUIDANCE_RULE` adds: the insight is the answer and nothing more; the appliesWhen is the question as quoted; the scope is `unit` only when the answer would differ for another employer, role or application; where and when it was asked enters neither. A unit-scoped memory takes the document's unit key, and with no unit open it is withheld as `unit-unnamed` (`packages/quality-loop/src/orchestrators/document-memory/read-document-digest.ts:48` `readDocumentDigest`).

_Read back later._

21. In the same unit of the same session, the cache answers (step 5). Anywhere else the stored fact must be recalled. Its condition is the quoted question, and a later form probes with the same question text (`packages/contracts/src/lib/browser-session/field-goal-evidence.ts:43` `fieldProbes`), so the two meet by design.

_teach-again, offline._

22. `browser-session teach-again --sessions <dir> [--tenant <name>] [--dry-run]` teaches recorded answers again from session dumps through the brain the settings choose — under the tenant named, else the environment's — (`packages/browser-session/src/modules/session/teach-again.ts` `teachAgain`). It reads each dump's `fields.json` and `teach.json` files (`packages/browser-session/src/modules/session/recorded-answers.ts` `readDump`) and keys each answer by its question; an item of a shape this build cannot read is named in the report, counted toward the teachings' order and taught by nobody. A newer item keeps the unit it names (`context.unitKey`) and the scope it declares (`about`); an older item that names none takes the unit open at its step (`recorded-answers.ts` `unitOpenAt`) and, while the loop still holds the digest run of its earlier teaching, the scope that digest gave its question — else no scope, left to the brain's rule, and counted (`teach-again.ts` `scopedAnswers`). It links answer _i_ to teaching _i_ only when the counts agree (`recorded-answers.ts` `answersOf`), teaches each unit's answers in batches of at most 16 (`packages/contracts/src/lib/browser-session/guidance.ts` `guidanceDocuments`) through one `teach` each, takes one receipt per answer, counts the outcomes per answer and links each row to its own answer's reference; only for an answer whose receipt says `queued` — the `loop` brain's — does it wait for the digest and retract the earlier digest runs, and only when the new digest stored everything (`teach-again.ts` `digestRunOf`).

**Data that crosses.**

| What                | Shape                                                                                                                                        | Code                                                                                 |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| the per-unit caches | a map from unit key (null outside any unit) to a map from question to value; one for operator answers, one for values the session typed      | `packages/browser-session/src/core/session-state.ts:48` `ByUnit`                     |
| the taught item     | `OperatorGuidanceDto {sessionId, capturedAt, field{question, type, options}, context{taskLabel, unitKey, page}, answer, about, chosen, via}` | `packages/contracts/src/lib/browser-session/guidance.ts:34` `operatorGuidanceSchema` |

| the decision row    | `browser_decision`, with `teaching_ref`                                                                                                      | `packages/db/src/entities/browser-decision.entity.ts:113` `teachingRef`              |

**Gotchas.**

1. **Live teaching is fire-and-forget.** `teach` returns once the orchestration opens. "taught through <id>" in the log and `teaching_ref` on the row mean "started", not "stored". The digest may still store nothing, and nothing retries it. A start that never reached the loop is asked again for up to 60 s (`packages/browser-session/config/session/standard.json:13` `loopRecovery`, handed to the client at `packages/browser-session/src/modules/session/session.module.ts:205` `loopRecovery`; `packages/loop-client/src/http-loop-client.ts:52` `repeatable`). A timeout, a refusal, or a start still unreachable after that window is logged as not taught and never retried.
2. **The next unit may ask again before the fact is stored.** The cache is per unit, so at Company B it is empty, and a digest takes minutes. Until it finishes, a form at Company B cannot see an answer given at Company A.
3. **An answer given outside any unit loses its unit-scoped fact**: the document names no unit, so the memory is withheld as `unit-unnamed`.
4. **The unit key is the declared facets, else a random task id** (`packages/contracts/src/lib/units/identity.ts:102` `unitKeyOf`; the id from `packages/browser-session/src/core/step-executor.ts:71` `openTaskUnlessRefused`). Two listings at one company are one unit, so the cache and unit facts cross between them. Without facets, unit facts are keyed by a UUID no later session will produce.
5. **A suggestion typed in the operator's place is never taught.** It is kept only as what the field now holds (`packages/browser-session/src/core/field-fill.ts:86` `settled`), not as an operator answer.
6. **A chosen invented draft becomes the subject's fact.** The taught section only adds ", choosing a drafted answer". The draft was labelled "invented — not in your record" when offered. With the working-tree setting `invented: fill`, an invented draft is typed unseen instead, and then nothing is taught.
7. **Enter alone means `/readback`** (`packages/browser-session/src/core/operator-interaction.ts:37` `FIELD_ENTER`). It teaches whatever the page holds, a site's pre-fill included.
8. **A live session can teach under the placeholder subject.** Only advisors require a declared subject (`packages/browser-session/src/core/unit-advice.ts:201` `subjectDeclared`); facts are otherwise taught for `the subject`.
9. **A field with no question text is asked again on every form.** The warning says the answer is "kept for this session only", but the caches skip a null key (`packages/browser-session/src/core/field-fill.ts:85` `settled`).
10. **`browser_decision.question` is the field's name, not the memory key** (`packages/browser-session/src/core/field-flow.ts:209` `question`). Radio questions often have an empty name, which skews "asked before" queries.
11. **After 12 hours a question can be answered only at the terminal.** The notifications prompt expires (`packages/notifications-client/src/interaction-client.ts:98` `PromptExpired`).
12. **Teaching blocks the form.** Each start is awaited before the next field: a POST with a 15 s timeout (`packages/loop-client/src/http-loop-client.ts:35` `READ_TIMEOUT_MS`), asked again for up to 60 s while the loop cannot be reached (gotcha 1).
13. **teach-again is not idempotent under the `loop` brain.** It only reads the dumps, so a second run takes its "earlier" digests from the original `teach.json` again: it retracts what the first run already removed, leaves the first run's new digests standing, and stores another copy. Its `retracted` count counts calls, not points. Under the `memory` brain a second pass is harmless: the same answer to the same question answers `unchanged`, and the report counts the outcomes.
14. **Do not run teach-again over the live dump directory.** Mid-form, `teach.json` already holds the new answer but `fields.json` does not, so the counts differ and the dump is taught again without linking or retracting.
15. **Linking is positional and per dump.** One lost `fields.json` or `teach.json` unlinks the whole dump, and nothing of it is retracted.
16. **The stored condition and the probe can differ for long questions.** The taught question is cut at 600 characters (`packages/browser-session/src/core/field-teach.ts:15` `excerpt`), while the probe is the full text.

## 5. Flow C — a form page gets its evidence and its answers (recall, answer, routing)

The session composes a goal for the page: the whole mission, the open unit of work, the fields, and a JSON index naming the pipeline and the unit key. It posts the goal to the `form-memory` orchestration. The orchestration's `recall` step makes no model call. Each distinct field question becomes one probe, searched against both named vectors, among document memories only, and among unit-bound memories only those of the page's unit. Each field's results are fused by reciprocal-rank fusion (RRF), the page's evidence is dealt out by rank up to 24 items, and the goal is composed again with that evidence under the aliases `m1`, `m2`…. The `target` step runs `field-answer` over that goal and reports the run's admission and the field locations its findings withhold. Back in the session, a fixed precedence routes each field to blank, keep, fill or the operator.

```text
browser session                      quality loop: form-memory                                Qdrant
 | composeFieldGoal(prose, fields, no evidence, index {pipeline, fields, unitKey})
 |-- POST /orchestrations/form-memory {pipeline: field-answer, goal, criteria, maxIterations: 1} ->|
 |                                    | refuseNonForm; context = {embedding, store.verify()}
 |                                    | step "recall" (no model call)
 |                                    |   splitFieldGoal -> fields, unitKey
 |                                    |   fieldProbes: one probe per distinct question text
 |                                    |   embed the probes (through the cache)
 |                                    |   searchProbes: 2 named vectors per probe,
 |                                    |     filter {kinds: document kinds, unitKey} ----------------->| queryBatch
 |                                    |   per field: fuse (RRF); per page: deal by rank, cap 24 <------|
 |                                    |   composeWithinBudget: goal + "## Evidence about the subject"
 |                                    | step "target": field-answer run over that goal
 |                                    |   producer -> validators -> critics -> evaluator -> controller
 |                                    |   report {admission, withheld[]}
 |<-- settled record; GET /runs/:id --|
 | routeFields: hidden? -> admission -> withheld at field.N -> answer, typed if fills[rests] = fill
 | withOperatorCache; suggestions prefetch; settle each field (asks go through Flow B)
```

**Steps.**

1. Each listed element becomes a `FieldSpec` with its ref, role, label, input type, options, current value, `required`, `invalid`, length limit, hidden traits and nearby words (`packages/contracts/src/lib/browser-session/field-goal.ts:73` `fieldSpecOf`; `packages/contracts/src/lib/browser-session/field-goal.ts:48` `fieldSpecSchema`).
2. The open unit is described for the form: label, url, facets and unit key, or null when no unit is open (`packages/browser-session/src/core/open-unit.ts:99` `formTaskOf`).
3. The prose half is the mission verbatim, then `## Open unit of work` (`packages/browser-session/src/adapters/loop-http/render-goal.ts:225` `renderFieldProse`). The mission is the whole goal file (`packages/browser-session/src/core/session-engine.ts:59` `mission`). Each pipeline's rubric is derived from it once, when the session starts (`packages/browser-session/src/core/session-engine.ts:57` `deriveRubrics`).
4. The goal is composed with no evidence yet (`packages/browser-session/src/adapters/loop-http/loop-brain.ts:85` `formRun`, then `packages/contracts/src/lib/browser-session/field-goal.ts:378` `composeFieldGoal`): the prose, `## Fields to answer` with one line per field (`packages/contracts/src/lib/browser-session/field-goal.ts:323` `renderFieldLine`), `## Evidence about the subject` saying nothing was recalled, `## Limits`, and the index `{pipeline, fields, evidence, unitKey?}` (`packages/contracts/src/lib/browser-session/field-goal.ts:370` `indexOf`). A goal past the budget becomes the `goal-budget` brain fault (`packages/browser-session/src/adapters/loop-http/loop-runs.ts:63` `LOOP_FAULTS`).
5. The session starts the orchestration with the pipeline, the goal, the criteria, one iteration and who opened it (`packages/browser-session/src/adapters/loop-http/loop-brain.ts:92` `startOrchestration`; `packages/browser-session/src/adapters/loop-http/loop-brain.ts:30` `DECISION_ITERATIONS`).
6. The orchestrator refuses a goal its codec did not write, or one composed for another pipeline (`packages/quality-loop/src/orchestrators/form-memory/definition.ts:28` `refuseNonForm`), and snapshots the store (`packages/quality-loop/src/orchestrators/form-memory/definition.ts:46` `context`). Its steps are `recall`, then `target`; `target` runs whether or not `recall` handed anything on.
7. Recall checks readiness (`packages/quality-loop/src/orchestrators/common.ts:89` `storeReadiness`: `embeddings-disabled`, `store-unavailable` or `store-empty`) and splits the goal back into prose, fields and unit key (`packages/contracts/src/lib/browser-session/field-goal.ts:414` `splitFieldGoal`), all inside `packages/quality-loop/src/orchestrators/form-memory/steps.ts:103` `recall`.
8. One probe per distinct question text, at most 40 (`packages/contracts/src/lib/browser-session/field-goal-evidence.ts:43` `fieldProbes`, the contracts' dealing helper beside the goal codec; the cap is `packages/contracts/src/lib/browser-session/field-goal-evidence.ts:18` `MAX_FIELD_PROBES`, the fields bound's target). Each probe's hit budget comes from the kind of control, a table the loop declares and hands the helper: 10 for a textarea, 3 for anything else (`packages/quality-loop/src/orchestrators/form-memory/probes.ts:45` `HITS_PER_FIELD_TYPE`). Two fields asking the same question share one probe, which takes the larger budget.
9. The probes are embedded, and one search is built per probe and named vector, all with the page's one filter (`packages/quality-loop/src/orchestrators/form-memory/probes.ts:72` `searchProbes`): kinds limited to the document kinds, plus the unit key when the goal names one (`packages/quality-loop/src/orchestrators/form-memory/probes.ts:66` `formEvidenceFilter`).
10. The store runs them as one `queryBatch`. Each search over-fetches three times its budget, then drops payloads it cannot read and texts it has already seen (`packages/quality-loop/src/modules/memory/qdrant/qdrant-memory-store.ts:105` `searchMany`; `packages/quality-loop/src/modules/memory/qdrant/qdrant-memory-store.ts:30` `DEDUPE_FACTOR`). The unit clause is spelled out in §6.
11. Fuse, then deal (`packages/quality-loop/src/orchestrators/form-memory/probes.ts:101` `fieldEvidence`). Each field's two lists are fused by RRF: a hit scores `1 / (60 + rank + 1)` for each list it appears in (`packages/quality-loop/src/orchestrators/memory/recall/fusion.ts:16` `fuse`; `packages/quality-loop/src/orchestrators/memory/recall/fusion.ts:14` `RRF_K`). Then the page's evidence is dealt by rank, every field's best before any field's second, one slot per distinct fact, up to 24 (`packages/contracts/src/lib/browser-session/field-goal-evidence.ts:75` `dealByRank`; `packages/contracts/src/lib/browser-session/field-goal.ts:45` `MAX_EVIDENCE`). No hit at all skips the step as `store-empty`.
12. Hits become evidence items (`packages/quality-loop/src/orchestrators/form-memory/probes.ts:127` `evidenceItems`): alias, text on one line cut to 1,200 characters (`packages/contracts/src/lib/browser-session/field-goal.ts:231` `evidenceText`), the day stored, the scope (a point with none reads `subject`), the kind, and the source — the pipeline that wrote it as `origin`, and `<runId>#<ref>` as `ref` (`packages/quality-loop/src/orchestrators/form-memory/probes.ts:119` `evidenceRef`).
13. The goal is composed again with as much evidence as fits the 64,000-byte budget, the lowest-ranked items dropped first (`packages/quality-loop/src/orchestrators/form-memory/steps.ts:79` `composeWithinBudget`). The evidence section opens with two legends: the kinds the composer declares as data — here the document kinds, `packages/contracts/src/lib/quality-loop/document-digest.ts:66` `DOCUMENT_MEMORY_LEGEND`, passed as `FieldGoalInput.kinds` and rendered by `packages/contracts/src/lib/browser-session/field-goal-terms.ts:32` `kindsLegend`; an item of a kind the legend does not list is refused by name — and the scopes, ending "A unit item settles only a field about the unit of work this goal names." (`packages/contracts/src/lib/browser-session/field-goal-terms.ts:36` `SCOPE_LEGEND`). When the goal names a unit, one more sentence says every unit item listed was recorded for a unit its mission identifies as this one (`packages/contracts/src/lib/browser-session/field-goal-terms.ts:50` `unitNamedLegend`). Each item is one line (`packages/contracts/src/lib/browser-session/field-goal.ts:342` `evidenceLine`).
14. The target step runs the form pipeline over that goal and reports `{admission, withheld}` (`packages/quality-loop/src/orchestrators/form-memory/steps.ts:152` `target`; `packages/quality-loop/src/core/outputs/withheld.ts:179` `withheldOf`). The runner checks the report's shape (`packages/quality-loop/src/orchestrators/runner/run-orchestration.ts:151` `checkedReport`, against `packages/contracts/src/lib/browser-session/pipelines.ts:37` `formTargetReportSchema`, which is the run readout's shape, `packages/contracts/src/lib/quality-loop/admission.ts:47` `runReadoutSchema` — the same `{admission, withheld}` every settled run now answers as `readout` on `GET /runs/:id`, read at the bar the run asked for).
15. The `field-answer` run (`packages/quality-loop/src/pipelines/field-answer/definition.ts:37` `FIELD_ANSWER`). The producer answers every field with where what it asks holds (`about`: `subject` or `unit`, declared whatever the decision, so an operator's answer to an unsettled field is taught under a declared scope), a decision (`answer`, `keep`, `ask-operator` or `leave-blank`), a value, the one word it rests on, the evidence aliases it cites and a reason (`packages/contracts/src/lib/browser-session/field-answers.schema.ts:26` `fieldAnswerSchema`). The `references` validator blocks; the `limits` validator only warns, and withholds what it names (`packages/quality-loop/src/pipelines/field-answer/validators.ts:119` `referencesValidator`; `packages/quality-loop/src/pipelines/field-answer/validators.ts:134` `limitsValidator`). The critics `grounding` and `form` judge, the evaluator reads their findings, and the standard controller decides. By finding type (`packages/quality-loop/src/pipelines/field-answer/definition.ts:155` `findingTypes`): `ungrounded`, `misfit_option`, `inconsistent` and the gated `trap_answered` withhold every field they name; `overstated` withholds only when its judge marks it `requires_user`; `needless_ask` and `blank_required` withhold nothing.
16. The session reads the result back (`packages/browser-session/src/adapters/loop-http/loop-brain.ts:16` `awaitOrchestration`, then `GET /runs/:id`). A report that does not parse reads as `fell-short` with nothing withheld.
17. Each field is routed (`packages/browser-session/src/core/field-routing.ts:76` `routeFieldsInSession`, then `packages/contracts/src/lib/browser-session/route-fields.ts:181` `fieldRoute`), first match wins:
    1. the page hides the field: leave it blank ("trap-skipped");
    2. the admission is `no-rubric` or `no-artifact`: unsettled;
    3. something is withheld at the field's position: unsettled;
    4. the run gave no answer for it: unsettled;
    5. otherwise the answer decides (`packages/contracts/src/lib/browser-session/route-fields.ts:129` `answerRoute`): a `keep` needs a value in the field; an answer equal to what the field holds is a keep; an answer is typed only when the `fills` table marks its `rests` word `fill`.

    An unsettled field goes to the operator when the page needs a value in it, and is left blank otherwise.

18. The `fills` table (`packages/browser-session/config/answering/standard.json:2` `"fills"`): `stated`, `restated`, `derived`, `mapped`, `inferred`, `composed` and `policy` fill; `none` asks, and the schema refuses anything else for it (`packages/contracts/src/lib/browser-session/answering.ts:45` `fills`). What each word means is one table, shown to the answerer and the judges alike (`packages/contracts/src/lib/browser-session/vocab.ts:178` `ANSWER_BASIS_MEANINGS`).
19. Then come the operator cache, the suggestions and the settling, as in Flow B steps 5 to 19. A fill the browser cannot perform stops the page.
20. One `browser_decision` row is recorded per field, and `fields.json` per step (`packages/browser-session/src/core/field-flow.ts:336` `dumpFields`).

The suggestions are a second `form-memory` orchestration with its own recall, running the `answer-suggestions` pipeline (`packages/quality-loop/src/pipelines/answer-suggestions/definition.ts:58` `ANSWER_SUGGESTIONS`). Each suggestion has a basis — `record`, `transfer` or `invented` — and record and transfer suggestions cite evidence.

**Data that crosses.**

| What             | Shape                                                                             | Code                                                                                         |
| ---------------- | --------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| a field          | `FieldSpec`                                                                       | `packages/contracts/src/lib/browser-session/field-goal.ts:48` `fieldSpecSchema`              |
| a probe          | `MemoryProbe {vector, using: condition or lesson, limit, filter}`                 | `packages/quality-loop/src/orchestrators/memory/ports.ts:150` `MemoryProbe`                  |
| a hit            | a stored memory plus its cosine score                                             | `packages/quality-loop/src/orchestrators/memory/ports.ts:117` `MemoryHit`                    |
| an evidence item | `{alias, text, when, scope, kind, source {origin, ref}}`                          | `packages/contracts/src/lib/browser-session/field-goal.ts:241` `evidenceItemSchema`          |
| the answers      | `{summary, fields[{ref, about, decision, value, rests, basis, reason}]}`          | `packages/contracts/src/lib/browser-session/field-answers.schema.ts:63` `fieldAnswersSchema` |
| the report       | `{admission, withheld[{ref, source, by, note}]}`                                  | `packages/contracts/src/lib/browser-session/pipelines.ts:37` `formTargetReportSchema`        |
| a routed field   | `{position, field, answer, route, value, source, reason, withheld}` plus `cached` | `packages/contracts/src/lib/browser-session/route-fields.ts:26` `FieldReadout`               |

**Gotchas.**

1. **One bad alias keeps every judge off the page, and the rest of the page is still filled.** A blocking validator problem keeps the artifact from every lens (`packages/quality-loop/src/core/loop/iteration.ts:122` `blocked`), so the run falls short. Routing escalates only on `no-rubric` or `no-artifact`, so every other field is filled on the model's own `rests` word, with no grounding or trap critic having looked.
2. **If the report drifts from its schema, all withholding turns off.** The runner nulls a report that does not parse; it logs `step target: report refused: …` and adds that to the step's note (`packages/quality-loop/src/orchestrators/runner/run-orchestration.ts:151` `checkedReport`), but the session never sees it and reads `fell-short` with nothing withheld. Only the page's own hidden-field facts still override the answers.
3. **Withholding goes by position.** Judges locate `field.N` by the answer's index in the artifact (`packages/quality-loop/src/pipelines/field-answer/output.ts:31` `locate`); the router matches by the field's index in the page. Keeping the order is only an instruction to the model, so a reordered artifact would withhold the wrong field.
4. **A field-level withholding of suggestions is ignored.** Only suggestion-level refs (`field.N.M`) are dropped (`packages/browser-session/src/core/operator-ask.ts:54` `offeredSuggestions`), so that field's record suggestion can still be typed.
5. **A value the page refused is not asked again when the session typed it.** `openOf` drops a field whose value equals what the session settled, and never reads `invalid` (`packages/browser-session/src/core/field-flow.ts:266` `openOf`).
6. **`store-empty` means two things.** Readiness counts every point in the collection, design lessons included (`packages/quality-loop/src/orchestrators/common.ts:89` `storeReadiness`). A step with zero document hits also says `store-empty`, so a store holding only lessons reads as empty.
7. **A field whose question first appears after the page's 40th distinct question gets no probe**, and so no evidence of its own (`packages/contracts/src/lib/browser-session/field-goal-evidence.ts:18` `MAX_FIELD_PROBES`). A page may list up to 50 fields; a field that repeats an earlier question still shares that question's probe (`packages/contracts/src/lib/browser-session/field-goal-evidence.ts:43` `fieldProbes`).
8. **Long stories are clipped** to 1,200 characters as evidence (`packages/contracts/src/lib/browser-session/field-goal.ts:44` `EVIDENCE_TEXT_MAX_LENGTH`), though a `profile_story` is meant to be kept whole.
9. **Long option lists eat the evidence budget.** Options are written in each field line and again in the index, beside the whole mission. Evidence is dropped first; if even the bare goal is too big, the page faults and every field the page needs a value in (required, or a radio group with nothing chosen) goes to the operator, unless the page hides it (`packages/browser-session/src/core/field-routing.ts:54` `faultedReadouts`).
10. **A cached operator answer skips the value checks** (`packages/browser-session/src/core/field-routing.ts:34` `withOperatorCache`). A select whose options differ on the next form can refuse it, which stops the page.
11. **Inferred values are typed without asking.** `inferred` fills, and it means "what adjacent evidence makes likely without stating it" (`packages/contracts/src/lib/browser-session/vocab.ts:185` `inferred`).
12. **Fusion favours hits that both vectors found**: with `RRF_K` 60, a hit in both lists (2/63) always beats the top of one list (1/61).
13. **Fields with options get no suggestions**, so a select or radio question sent to the operator is never auto-typed (`packages/browser-session/src/core/operator-ask.ts:155` `for`).
14. **A recall failure shows up only as extra asks.** A failed or skipped `recall` does not fail the orchestration; the target runs on the goal with no evidence, which tells the answerer to route such fields to the operator (`packages/contracts/src/lib/browser-session/field-goal-terms.ts:62` `FORM_GOAL_TERMS`). Look at `steps.recall` in `GET /orchestrations/:id` to tell.
15. **`fields.json` shows the wrong goal size.** `composition.bytes` measures the goal before evidence was added (`packages/browser-session/src/adapters/loop-http/loop-brain.ts:129` `composition`). The real goal is the child run's `request.goal`.
16. **With the working-tree drafts setting, drafts are typed unseen.** `transfer: fill` and `invented: fill` make `fillableSuggestion` type the first suggestion of any basis into a free-text field that would have gone to the operator (`packages/browser-session/src/core/operator-ask.ts:201` `fillableSuggestion`). The schema's own comment calls a typed invented draft "experience the record does not hold, submitted unseen" (`packages/contracts/src/lib/browser-session/answering.ts:40` `invented`).

## 6. Scope and the unit key

A fact either holds of the subject wherever it is asked, or only of the one employer, role or application it was recorded for. The second kind must not leak into another application. Two pieces of data enforce this: a scope on every document memory, and a unit key on every unit-scoped one. The store's filter, not a model, keeps other units' memories out of a search.

**The rules.**

1. **Two scopes, one test.** The scopes are `subject` and `unit` (`packages/contracts/src/lib/units/scope.ts:12` `MEMORY_SCOPES`). The digest decides each memory's scope by one test: would the answer differ for another employer, role or application? Unit where it would — working or knowing someone there, consents, how the opening was heard of, whether this posting suits; subject where it is the same whoever asks (`packages/contracts/src/lib/quality-loop/document-digest.ts:117` `SCOPE_RULE`). The `field-answer` producer applies the same test to every field it answers and declares the result as `about` (its `producer.md`), so an operator's answer is taught under a scope the answerer judged, not one argued from wording. The grounding critic faults a wrong scope as `misscoped_fact`, which gates the run and withholds the memory (`packages/quality-loop/src/pipelines/document-digest/definition.ts:35` `SCOPE_FINDING_TYPE`).
2. **A document may declare one scope for all its memories** (memory-ingest's `--scope subject`). The declaration overwrites whatever the digest wrote (`packages/quality-loop/src/orchestrators/document-memory/read-document-digest.ts:48` `readDocumentDigest`). The goal leaves the scope test out of its rules (`packages/contracts/src/lib/quality-loop/document-digest.ts:189` `rulesOf`) and says so in its limits (`packages/contracts/src/lib/quality-loop/document-digest.ts:185` `declaredScopeLimit`), and a scope finding withholds nothing.
3. **A file can never declare `unit`**, because a file names no unit of work (`packages/memory-ingest/src/config.ts:39` `INGEST_SCOPES`).
4. **A unit-scoped memory must carry a unit key.** The document's index carries the key (`packages/contracts/src/lib/quality-loop/document-digest.ts:148` `indexOf`), and the reader stamps it on every unit-bound memory. A document with no key has those memories withheld as `unit-unnamed`. A document that declares a unit-bound scope and names no unit is refused with 400 before any row exists (`packages/quality-loop/src/orchestrators/document-memory/definition.ts:32` `refuseNonDocument`).
5. **The key is the unit's declared identity, else its id** (`packages/contracts/src/lib/units/identity.ts:102` `unitKeyOf`). It names no mission, so two missions that declare the same facets read each other's unit memories.
6. **Who reads what.** A memory with no scope, or scope `subject`, is read by every search. A `unit` memory is read only by a search that names its key; a search that names no key reads none of them.

**Where each piece is written and read.**

**The store's filter clause.** Every search's filter carries one `must_not` from `unitExclusion`, built from the table of bound scopes (`packages/contracts/src/lib/units/scope.ts:37` `UNIT_BOUND_SCOPES`):

```text
search names no unit:
  must_not: [ { key: "scope", match: { any: ["unit"] } } ]

search names the unit "company=acme":
  must_not: [ { must:     [ { key: "scope",   match: { any: ["unit"] } } ],
                must_not: [ { key: "unitKey", match: { value: "company=acme" } } ] } ]
```

In words: leave out every unit memory whose key is not this unit's, and all of them when no unit is named. A point with no `scope` matches no clause, so it is always read. The exclusion sits inside the filter, so a slot an excluded memory would have taken is refilled from below.

**The in-memory fake.** Fast specs use `packages/quality-loop/src/modules/memory/testing.ts:117` `InMemoryMemoryStore`. Its filter, `packages/quality-loop/src/modules/memory/testing.ts:89` `passes`, mirrors the rule by hand: a memory passes if it is not unit-bound, or if the search names its key. Its comment explains why a spec holds the fake and the adapter to the same hits on a real Qdrant, and another spec pins the Qdrant clause itself (`packages/quality-loop/src/modules/memory/qdrant/qdrant-memory-store.filter.spec.ts:30` `[QL-71]`). One difference remains: the fake fills a probe's limit whenever that many distinct points pass the filter, while Qdrant fetches three times the limit and can return fewer after deduping and skipping unreadable points.

**Legacy points.**

- A document memory stored before scopes existed has no `scope`. Every search reads it, and the evidence lists it as `subject` (`packages/contracts/src/lib/units/scope.ts:23` `DEFAULT_MEMORY_SCOPE`, read at `packages/quality-loop/src/orchestrators/form-memory/probes.ts:127` `evidenceItems`).
- A unit memory stored before unit keys existed has no key, so no search reads it. Commit `dcb2fc71` introduced the keys, and teach-again is how those answers are taught again under a key.
- A document memory stored before kinds existed was filed as `lesson`, the document writer's first owned kind. Form recall asks only for the document kinds, so forms never see it; design recall sets no kind filter and still does.

**What a misscoped answer costs.** A made-up example: the operator answers two questions at Company A, and the same two come up at Company B.

```text
Company A form   "Have you worked for this company before?"      operator: "Yes"
                 "Are you authorized to work in this country?"   operator: "Yes"

right scopes     worked-here  -> unit, key "company=company a"
                 authorized   -> subject (no key)

Company B form   worked-here: Company A's memory is filtered out; the field goes to the
                 operator, who answers for Company B; that answer is stored under
                 "company=company b"
                 authorized: recalled as subject evidence and typed (rests `restated`)
```

- **A unit fact stored as subject.** If worked-here were scoped `subject`, Company B's evidence would list "Yes" as a fact about the subject, and the answerer could type "Yes" for an employer the subject never worked for: a false statement on an application. Three things stand against it: the gated, withholding `misscoped_fact`; the legend line "A unit item settles only a field about the unit of work this goal names"; and the mission's rule that a question about the employer is settled by the standing answers and the record of employers, never by an answer about another employer (`packages/browser-session/goals/linkedin-easy-apply.md:59` `standing answers`).
- **A subject fact stored as unit.** If authorized were scoped `unit`, it would be stored under `company=company a` and be invisible at Company B, so the operator would be asked at every company. The scope design exists because of this cost: the comment above `packages/contracts/src/lib/units/scope.ts:12` `MEMORY_SCOPES` records one fact asked five times across four sessions (measured 2026-10-12).
- **No keys at all.** Before unit keys, every search read every unit's answers. Commit `dcb2fc71` measured, over 15 questions about an organisation, answers given in other units holding 29 of the 45 evidence slots.
- **A wrong key.** The key is the company as the planner read it off the page. Nothing checks the value against the page, and keys do not merge spelling variants (`packages/contracts/src/lib/units/identity.ts:49` `facetKey` keeps "Acme Corp" apart from "Acme"), so one misreading splits a company's memories in two (§7).

## 7. Flow D — applications as units of work

An application is a unit of work. The mission declares the page fact that identifies a unit (`company`) and the advisor that keeps a record of units across sessions (`job-application`). Before every plan, the session asks that advisor what is on record for the subject. Units to avoid become prose for the planner; forbidden units go into the step goal's index, where a validator cuts any `taskStart` that matches one. A `taskStart` mints the unit's id, writes a `browser_task` row and publishes `session.unit.opened`; `taskDone` closes the unit and publishes `session.unit.closed`. The job-application service turns those events into `job_application` rows and derives each company's stance from a declared policy. While a unit is open, its key rides on every form goal and every taught answer.

```text
mission file     browser session                            job-application :3006         bus :3005
 | ## Unit identity: company   ## Advisors: job-application
 |--------------->| resolveAdvisors: GET /advisor, POST /advice (first advice) ->|
 |                | session.started --------------------------------------------------------->|
 |                |                                            |<---- intake pulls events ---|
 |                |                                            | started: abandon this profile's
 |                |                                            |   older in-progress rows
 | every step     | recallAdvice: POST /advice --------------->| unitsOnRecord: a stance per company
 |                |<---------- {units [{identity, stance, note}], omitted}
 |                | composeStepGoal: avoid -> prose; forbid -> index.unitsForbidden
 |                | browser-step limits validator cuts a forbidden taskStart
```

**Steps.**

_Declaration._

1. The mission declares the unit, its identity and its advisor (`packages/browser-session/goals/linkedin-easy-apply.md:5` `## Unit of work`; `packages/browser-session/goals/linkedin-easy-apply.md:13` `## Unit identity`, whose one line is `- company: …`; `packages/browser-session/goals/linkedin-easy-apply.md:21` `## Advisors`, whose one line is `- job-application`).
2. Both sections are parsed (`packages/contracts/src/lib/units/mission-identity.ts:101` `unitFacetsOf`; `packages/contracts/src/lib/units/mission-identity.ts:105` `advisorsOf`), and a malformed one is refused (`packages/contracts/src/lib/units/mission-identity.ts:44` `MissionIdentityMalformed`).

_Handshake, before any row._

3. Where advisors run comes from `UNIT_ADVISOR_URLS` (`packages/browser-session/src/config.ts:181` `advisorEntries`), each made into an HTTP advisor (`packages/browser-session/src/modules/session/session.module.ts:96` `configuredAdvisors`; `packages/browser-session/src/adapters/advisor-http/http-unit-advisor.ts:50` `HttpUnitAdvisor`).
4. Before the session may open (`packages/browser-session/src/core/session-engine.ts:79` `runSession`), `packages/browser-session/src/core/unit-advice.ts:193` `resolveAdvisors` checks that the sections parse, that the session has a subject of its own, that each named advisor describes itself under its own id, that it keeps its record only by facets the mission declares, and that a first advice call answers. Any failure refuses the session with exit 2.
5. The service says who it is — the id `job-application` and the facet `company` (`packages/job-application/src/applications/record-source.ts:126` `describe`) — on `GET /advisor` (`packages/job-application/src/advisor/advisor.controller.ts:22` `@Get(ADVISOR_ROUTES.describe)`), and answers 400 to an advice request that does not compare on `company`.
6. The session opens its ledger row and publishes `session.started` (`packages/browser-session/src/core/session-events.ts:70` `startedEvent`; topics in `packages/contracts/src/lib/units/session-events.ts:16` `SESSION_TOPICS`) through the bus (`packages/browser-session/src/adapters/notifications-http/bus-session-events.ts:8` `BusSessionEvents`).
7. The intake reads a new session on the same profile and subject as proof the earlier one died, and abandons its in-progress rows (`packages/job-application/src/intake/session-events.consumer.ts:68` `apply`; `packages/job-application/src/applications/session-record.ts:30` `started`).

_Every step: consult, then compose._

8. The advisor is asked before every plan (`packages/browser-session/src/core/step-flow.ts:105` `decide`, then `packages/browser-session/src/core/unit-advice.ts:258` `recallAdvice`). On a fault the session plans on the advisor's last good answer, marked `stale`, with one warning. Each answer is dumped as `01-steps/NN/advice.json`.
9. The service computes stances (`packages/job-application/src/applications/record-source.ts:130` `unitsOnRecord`). It reads the subject's rows inside the policy window, leaves out the asker's own open unit (`packages/job-application/src/applications/record-source.ts:40` `ownOpenUnit`), groups the rows by `identity_key`, scores each row by its status (`packages/job-application/src/applications/policy.ts:58` `stanceOf`), makes a company `forbid` if any row earns it and `avoid` otherwise, adds a note such as "in progress in another session since <date>", and sorts forbidden companies first (`packages/job-application/src/applications/record-source.ts:75` `onRecord`).
10. The step goal is composed with the answer (`packages/contracts/src/lib/browser-session/step-goal.ts:306` `composeStepGoal`). `## Units of work` lists this session's units, then the record's, forbidden first and at most 40 (`packages/contracts/src/lib/browser-session/step-goal-units.ts:68` `onRecordLines`). The limits state the facet rule and the forbidden rule (`packages/contracts/src/lib/browser-session/step-limits.ts:118` `limitsLines`). The index carries `unitFacets` and `unitsForbidden` (`packages/contracts/src/lib/browser-session/step-index.ts:196` `indexOf`). Units to avoid are prose only.
11. The `browser-step` limits validator cuts a `taskStart` whose facet names are not exactly the declared ones (`packages/quality-loop/src/pipelines/browser-step/validators.ts:259` `facetsFault`), or whose facets match a forbidden identity (`packages/quality-loop/src/pipelines/browser-step/validators.ts:288` `forbiddenFault`, comparing with `packages/contracts/src/lib/units/identity.ts:106` `matchesRecord`). The plan runs only up to the cut (`packages/contracts/src/lib/browser-session/route-plan.ts:28` `routePlan`), and a cut at the first action refuses the plan (`packages/browser-session/src/core/step-flow.ts:202` `refusePlan`).

_Open._

12. `taskStart` opens the unit (`packages/browser-session/src/core/step-executor.ts:71` `openTaskUnlessRefused`): a new UUID, the label, url and facets, a `browser_task` row (`packages/browser-session/src/adapters/mikro-orm/mikro-orm-ledger.ts:140` `openTask`), and `session.unit.opened` (`packages/browser-session/src/core/session-events.ts:83` `unitOpenedEvent`). When a unit is already open it does nothing, and the history says so.
13. The record inserts the application (`packages/job-application/src/applications/session-record.ts:40` `opened`): the company from the facets (`packages/job-application/src/applications/application.ts:33` `companyOf`), the unit's UUID as `id`, `companyKey(company)` as `identity_key` (`packages/job-application/src/applications/session-record.ts:82` `rowOf`), status `in-progress`, and an expiry `maxMinutes` after the open. While it is in progress, other sessions see the company as `forbid`.

_Inside the unit._

14. Every decision row carries the open unit's id (`packages/browser-session/src/core/engine-context.ts:147` `record`).
15. Every form goal names the unit (`packages/browser-session/src/core/open-unit.ts:99` `formTaskOf`), and every taught answer carries its key (`packages/browser-session/src/core/field-teach.ts:57` `remember`); see §6.
16. For this mission the identity is one facet, so the unit key `company=<facetKey(value)>` is the same string as `job_application.identity_key` (`packages/job-application/src/applications/application.ts:29` `companyKey`). The ids line up as well: the unit's UUID is `browser_task.id`, `job_application.id` and `browser_decision.task_id`.

_Close and end._

17. `taskDone` closes the unit (`packages/browser-session/src/core/step-executor.ts:155` `closeTask`): the task status by outcome (`packages/contracts/src/lib/browser-session/vocab.ts:100` `TASK_OUTCOME_STATUS`), the last 10 closed units kept for the next goal, the ledger row closed, and `session.unit.closed` published (`packages/browser-session/src/core/session-events.ts:92` `unitClosedEvent`).
18. The record closes the application: done becomes `submitted`, already-done `submitted-before`, skipped `skipped`, failed `failed` (`packages/contracts/src/lib/job-application/vocab.ts:20` `TASK_OUTCOME_APPLICATION_STATUS`; `packages/job-application/src/applications/session-record.ts:53` `closed`).

21. The policy file (`packages/job-application/config/policy/scatter.json:2` `windowDays`): a 90-day window; `in-progress` is `forbid`; `submitted`, `submitted-before`, `abandoned`, and since 2026-10-29 `failed` and `skipped`, are `avoid`; `neverOnRecord` is empty; `skippedBecomesAvoidAfter` is null (moot while set-asides are avoided outright).

**Gotchas.**

1. **Only 40 units on record reach the `## Units of work` prose, and `avoid` is never enforced.** The rest are counted as "(N more on record not listed)". Every forbidden unit the advisor returns — it answers with at most 200 (`packages/contracts/src/lib/units/vocab.ts:92` `ADVICE_UNITS_BOUND`) — still reaches the Limits line and the index, so forbid holds past 40; avoid is prose only. One session's first advice on 2026-10-14 already held 43 units, all `avoid`, and the 90-day window keeps the list growing.
2. **Facet values are the planner's reading of the page, never checked against it.** The validator checks facet names only (`packages/quality-loop/src/pipelines/browser-step/validators.ts:259` `facetsFault`). A variant spelling splits the record, slips past avoid and forbid, and gets a memory scope of its own.
3. **Forbid is eventually consistent, not a lock.** Events go out through an async queue, the intake applies them by long poll, and they count only at the next plan's consult. The docs accept the gap: two sessions can choose the same card within one planning window (`docs/job-application/overview.md:121` `two sessions choosing the same card`).
4. **A replay is not "nothing new".** The record stamps rows with the bus's publish time, so a replayed close moves `closedAt` and restarts the 90-day window, and it overrides a hand correction. Every replay begins with `session.started`, which abandons in-progress rows of any other session on the same profile and subject — a live one included.
5. **The intake acknowledges an event even when applying it failed.** `apply` logs "passed over" and the loop acks anyway (`packages/job-application/src/intake/session-events.consumer.ts:68` `apply`). Only `replay-events` recovers it.
6. **A crashed session's unit stays forbidden until a new session starts on the same profile and subject, or for up to 13 hours 10 minutes.** Nothing publishes a close for it. A new session there abandons it (step 7); otherwise it reads as abandoned only once it expires, at the open time plus the session's whole lifetime (`maxMinutes` 720 and `unitGraceMinutes` 70 in `packages/browser-session/config/session/standard.json:6-8`, published together as the event's `maxMinutes`; `packages/job-application/src/applications/policy.ts:46` `standingOf`). Abandoned, it is `avoid`.
7. **"abandoned" means two things.** In `browser_task` it is a unit closed `skipped` (`packages/contracts/src/lib/browser-session/vocab.ts:100` `TASK_OUTCOME_STATUS`); in `job_application` it is a unit left open when its session ended.
8. **The key is the company, not the listing.** Every listing at one company shares one key, across sessions and missions, so cached answers and unit memories carry between roles at that company.
9. **Choosing a forbidden card again and again can end the session.** The cut at the first action refuses the plan, and three refusals in a row trip the failure rail (`packages/browser-session/config/session/standard.json:8` `maxConsecutiveFailures`).
10. **`failed` and `skipped` are avoided since 2026-10-29**, so a listing that failed or was set aside is not opened again for the window; until then it earned no stance and was opened again every session, spending a task each time.
11. **A mission that names an advisor needs an explicit subject.** With the placeholder `the subject`, the session is refused before any row (`packages/browser-session/src/core/unit-advice.ts:201` `subjectDeclared`).
12. **The facet limit is effectively 6, not 4.** The mission section is parsed against the bound's ceiling (`packages/contracts/src/lib/units/vocab.ts:62` `UNIT_FACETS_BOUND`).

## 8. Flow E — design lessons and coaching recall (general engineering experience)

Design lessons are engineering experience, not facts about the subject. When a coach run in the studio completes, the studio hands it to the `memory` orchestrator. That orchestrator runs the `experience-digest` pipeline over what the run showed, and stores each lesson the digest endorses as a `lesson` point under the coach run's id. When the next coach run starts, it asks for recall. One shared routine derives search probes with a model, searches both vectors, fuses the hits, screens out what the producer already holds (only when the coach starts from a graded revision), has the `memory-recall` pipeline curate the candidates, and briefs only the producer with what it kept. Lessons never reach a form, because form recall asks for document kinds only.

```text
studio-api                       quality loop                                                 Qdrant

 |                                | recallLessons -> MemoryRunRecall.recall
 |                                |   focus: the adopted iteration's findings and criteria
 |                                |   probes: goal + focus lines + derived (one model call)
 |                                |   embed; searchMany with no kind filter ------------------->|
 |                                |   fuse (RRF) <----------------------------------------------|
 |                                |   screen what the producer holds (adopted runs only)
 |                                |   memory-recall run: the curator keeps <= 8 of <= 16
 |                                |   provenanceOf -> quality_run.recall
```

11. **Without `OPENAI_API_KEY`, nothing is recalled or learned**: recall skips as `embeddings-disabled`, and the digest step skips before any digest runs.
12. **A name clash.** The `experience-digest` pipeline digests what a finished run taught; it has nothing to do with the studio's experience profiles (§9).

## 9. Flow F — the studio's experience profiles (practice prompts, practice marks, export)

The studio keeps a small seeded table of experience profiles. Each row says whose it is through `origin`: `own` is the subject's real record, and `practice` is an example written only to practise on. ## 10. Removing and correcting facts

The store loses facts in two sizes: a whole digest run, or one point. Most corrections are made by teaching again — ingesting an edited document, or running teach-again over recorded answers — and each of those retracts the old digests only after the new ones are stored (make before break). Re-index is the only tool that puts points back, and it covers design lessons only. The loop records no retraction: a point retraction is recorded nowhere, and a re-index can bring back a retracted lesson. The one record is memory-ingest's manifest, which marks each digest run it retracted with `retractedAt` and `retractedPoints` (`packages/memory-ingest/src/core/record.ts:259` `markRetracted`). No code in the repository backs up the store.

| Size                       | Tool                                           | Code                                                                                                                                                                                                                                                                                  | Effect                                                                             |
| -------------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| one run                    | `DELETE /memory/:id`                           | `packages/quality-loop/src/modules/memory/memory.controller.ts:40` `@Delete(':id')`, then `packages/quality-loop/src/modules/memory/memory.service.ts:160` `retract` and `packages/quality-loop/src/modules/memory/qdrant/qdrant-memory-store.ts:156` `retractRun`                    | counts, then deletes every point whose `runId` matches; answers `{runId, removed}` |
| one point                  | `DELETE /memory/:id/points/:ref`               | `packages/quality-loop/src/modules/memory/memory.controller.ts:62` `@Delete(':id/points/:ref')`, then `packages/quality-loop/src/modules/memory/memory.service.ts:175` `retractPoint` and `packages/quality-loop/src/modules/memory/qdrant/qdrant-memory-store.ts:171` `retractPoint` | answers `removed {text, kind, scope}`, or `null` when nothing went                 |

| lessons, restored          | `POST /memory/:id/reindex`                     | `packages/quality-loop/src/modules/memory/memory.controller.ts:29` `@Post(':id/reindex')`, then `packages/quality-loop/src/modules/memory/memory.service.ts:109` `reindex`                                                                                                            | re-embeds a memory run's lessons from its stored digest                            |

**Which id to pass.** For a fact about the subject, the run id is its digest run. For a lesson or a knowledge item, it is the run it was learned from (the controller's comment above `packages/quality-loop/src/modules/memory/memory.controller.ts:62` `@Delete(':id/points/:ref')` says so). A form goal's evidence line gives one point's address, as in `… · document-digest <runId>#memory.3` (`packages/contracts/src/lib/browser-session/field-goal.ts:342` `evidenceLine`; `packages/quality-loop/src/orchestrators/form-memory/probes.ts:119` `evidenceRef`). So does every retrieval-report hit, `{runId, ref, score, text}` (`packages/quality-loop/src/modules/memory/reports/form-report.ts:41` `asHit`).

**Retiring a document, step by step.**

1. Parse the command and take the lock (`packages/memory-ingest/src/cli.ts:224` `execute`). `--dry-run` takes no lock and changes nothing.
2. Key each path relative to the working directory; a path the manifest does not hold is refused with exit 2 (`packages/memory-ingest/src/core/retract.ts:179` `NotInManifest`). Collect the document's digest runs (`packages/memory-ingest/src/core/retract.ts:128` `retirementOf`).
3. Retract one run at a time (`packages/memory-ingest/src/core/retract.ts:78` `retractRuns`, through `packages/loop-client/src/http-loop-client.ts:172` `retractMemory`).
4. Mark every entry that names the run with when it went and how many points went, and save after each run (`packages/memory-ingest/src/core/record.ts:259` `markRetracted`). The first failure stops the batch and leaves the remaining runs standing, with exit 1.

**Make before break.** A re-ingest posts the changed chunks first. Only when every chunk of the current plan is covered does it retract the document's other digest runs (§3, step 24). A chunk that halts, is refused, fails, or stores with `unit-unnamed` holds the replacement back, so the old and new digests stand side by side until a later run covers the whole document. teach-again works the same way per document of answers: it retracts the earlier digests only when the new digest stored and gave no reason.

**Correcting one fact.** Retract the point, then teach the right fact: edit the document and ingest it again (with the same `--date`, only the changed chunks are posted), or answer the field again at the next form. Live teaching never retracts the older answer, so a corrected answer stands beside the old one until the old point is retracted.

**Re-index, and its limits.**

- It accepts only `memory` orchestration ids; a `document-memory` or `knowledge` id answers 404.
- It rewrites only `lesson` points, from the digest already stored, under today's acceptance bar.
- The loop records no retraction, so a re-index stores again a lesson that was retracted from the run.
- If today's policy no longer admits the digest, the replace runs with zero chunks and deletes the run's lessons, answering `complete` with `chunks: 0` (read from the code).
- Retracted document facts come back only by ingesting again. A retracted posting no longer covers its chunk, so a plain re-run posts it.

**Backups.**

- The store keeps nothing of a point once it is gone. The retraction's answer carries its text, kind and scope; its log line carries the kind and text only (`packages/quality-loop/src/modules/memory/memory.service.ts:175` `retractPoint`). Save that answer if you may want the fact back.
- The manifest is the only link from a document's path to its digest runs. Copy `static/memory-ingest/manifest.json` before any destructive step: lose it, and the runs can be found only by hand, from the orchestration records (§2, gotcha 8), and retracted only by hand.
- No code under `packages/` or `scripts/` makes or reads a backup. The folders `static/memory-ingest/backup-2026-10-14`, `backup-2026-10-14b`, `slice1` to `slice3`, `narrative-a` and `narrative-b` were made by hand. `backup-2026-10-14b` holds, among other files, a `points.jsonl` of 1,270 lines and a `retracted-points.result.json` that records six point removals the manifest does not show.
- The documents are the real source. Keep the files you ingest; an exported `studio-experiences.md` is gitignored.

**Hazards.**

1. **`DELETE /memory/:id` ignores kind.** Design lessons and knowledge items are both filed under the run they were learned from, so a hand-typed DELETE with that run's id erases both writers' points.
2. **The wrong id removes nothing, silently.** The orchestration id in place of the digest run id answers 200 with `removed: 0`.
3. **A trailing slash retracts the whole run.** `DELETE /memory/<run>/` matches the run route, because strict routing is off; only the literal `points` segment protects the point route.
4. **An unreadable point answers `removed: null`, as an absent one does, and stays.** Only the log tells the two apart.
5. **Point retraction has no client and no UI.** It is curl only.
6. **The controller's comment says a run is retracted "before its new digest lands"** (`packages/quality-loop/src/modules/memory/memory.controller.ts:40` `@Delete(':id')`). Both callers retract after the new digest is stored.
7. **Retraction touches neither the `memory_support` rows nor the embedding cache.**
8. **Retraction depends on the embeddings setup.** With embeddings off the call errors; with a different model it hits another collection and removes 0, yet memory-ingest still marks the entries retracted, with `retractedPoints: 0`, and never asks that run again.
9. **A new `--date` or a rules change renames every chunk**, so the whole document is posted again before its old digests go.
10. **A 5xx or an unreachable loop is retried for 60 s; a 15 s timeout is not.** Either way the runs are left standing with exit 1, and the next run finishes the job.
11. **A store retraction does not clear a running session's per-unit answer cache.**

## 12. Worked examples (made-up data)

Every name, date and answer below is invented. The subject's record is assumed to hold three dated roles: Company A from 2021-03 to now, Company B from 2018-06 to 2021-02, and Acme from 2015-01 to 2018-05 — except in example (a), where Acme has never been seen at all.

### (a) "Do you currently work for Acme?" at a company never seen before

_Setup._ For this example only, the record holds the Company A and Company B roles and nothing about Acme: no `job_application` row, no memory recorded for an Acme unit. The session opens a listing at Acme, and the form asks a required radio question, "Do you currently work for Acme?", with the options Yes and No.

1. **The unit.** The plan's `taskStart` carries `company: "Acme"`, so the unit key is `company=acme` (`packages/contracts/src/lib/units/identity.ts:49` `facetKey` lower-cases it). The advisor has nothing on record for Acme, so nothing is avoided or forbidden. The open event makes Acme `forbid` for other sessions while the application is in progress; once it closes, `submitted` makes it `avoid` (`packages/job-application/config/policy/scatter.json:4` `"in-progress"`).
2. **Open fields.** Nothing was settled in this unit yet, so the field is a question (`packages/browser-session/src/core/field-flow.ts:266` `openOf`).
3. **Recall.** One probe: the question text, plus any words beside the field. A radio question takes 3 hits per vector. The filter asks for document kinds only and leaves out every unit memory whose key is not `company=acme` — here, all of them. What can come back is subject facts, for example:

   ```text
   - [m1] profile_fact · subject — The subject has worked as a software engineer at Company A
     since 2021-03; the end is open, computed to the document's date: 5 years 7 months. · stored
     2026-10-13 · document-digest 8c1f…#memory.2
   ```

4. **Answer.** The mission settles a question about the employer by the standing answers and the record of employers, never by an answer about another employer (`packages/browser-session/goals/linkedin-easy-apply.md:59` `standing answers`). A record whose current role is at Company A can carry `No`, citing m1, as `derived` or `mapped`; both words fill (`packages/browser-session/config/answering/standard.json:2` `"fills"`), so `No` is typed.
5. **Or ask.** If the record names no current role, or a judge confirms `ungrounded` (or `overstated` marked `requires_user`) at that field, the field is unsettled. A radio group with nothing chosen needs a value (`packages/contracts/src/lib/browser-session/route-fields.ts:85` `needsValue`), so it goes to the operator.
6. **Teach.** The operator answers `No`. The answer is cached under `company=acme` and taught as a guidance document whose head carries `unitKey: company=acme`. The scope test reads "working … there" as unit, so the stored memory has `scope: unit`, `unitKey: company=acme`, and the quoted question as its condition.
7. **Later.** At another Acme listing, in this session or any other, the memory comes back as `[m1] profile_fact · unit — …`, with the legend sentence that every unit item listed was recorded for this unit. At Company B the filter leaves it out, and the question there names Company B anyway.

### (b) An answer given at Company A, then the same question at Company B

_Setup._ One session applies at Company A, then at Company B. The Company A form asks two questions no memory settles yet:

- Q1, "Will you now or in the future require visa sponsorship?" — the operator answers `No`.
- Q2, "Do you know anyone who currently works here?" — the operator answers `Yes`.

_At Company A_ (key `company=company a`):

1. Both answers go into the unit's caches (`packages/browser-session/src/core/session-state.ts:48` `ByUnit`), and each is taught as its own guidance document whose head names `company=company a` (`packages/contracts/src/lib/browser-session/guidance.ts:149` `guidanceDocuments`).
2. The digests apply the scope test. Q1 is the same whoever asks: `subject`, stored with no key. Q2 depends on who the employer is: `unit`, stored with `unitKey: company=company a`.
3. A second listing at Company A is the same unit, so the cache fills both fields without asking (`packages/browser-session/src/core/field-routing.ts:34` `withOperatorCache`).

_At Company B_ (key `company=company b`):

4. The cache for `company=company b` is empty.
5. Q1: once Q1's digest has stored its fact, recall returns it as subject evidence, and `No` is typed, resting on it as `stated` or `restated`. If the Company B form comes before that digest finishes — digests take minutes, and teaching does not wait — nothing is recalled and the operator is asked again.
6. Q2: Company A's memory is left out by the store's filter. No evidence settles the field, so the operator is asked. The new answer is stored under `company=company b`.

_If Q2 had been scoped `subject`._ The guidance rule keeps where and when an answer was given out of the fact, so the stored insight would say only that the subject knows someone who works there. At Company B the identically worded question would find it, and `Yes` could be typed for a company where the subject knows no one. This is why `misscoped_fact` gates the digest and withholds the memory (`packages/quality-loop/src/pipelines/document-digest/definition.ts:35` `SCOPE_FINDING_TYPE`).

### (c) An employment-history block

_Setup._ A form page titled "Work experience" shows two groups of fields — "Job title", "Company", "From", "To" and a checkbox "I currently work here" — and names no employer.

_What the evidence holds._ Each field's probe is its label and the words beside it (`packages/contracts/src/lib/browser-session/field-goal.ts:136` `fieldQuestionOf`), such as `Company. Work experience 1`. Each takes 3 hits per vector, and the page deals up to 24 distinct facts, every field's best first. The three dated roles would typically appear as `profile_fact · subject` items, each with both ends and the span in years and months, as the document rules ask (`packages/contracts/src/lib/quality-loop/document-digest.ts:125` `DOCUMENT_RULES`).

_What the answer must do._ The mission says a section that names no employer lists the positions on record most recent first, each later section the next, every field of a section from its one position; a section that cannot describe a position still held passes over it; and a position still held is marked current where the section allows (`packages/browser-session/goals/linkedin-easy-apply.md:59` `employment-history`). So group 1 should be Company A with "I currently work here" ticked, and group 2 Company B.

_Why a group is still asked._

- A group mixing two roles is `inconsistent`, which withholds every field it names (`packages/quality-loop/src/pipelines/field-answer/definition.ts:165` `inconsistent`); a value no listed evidence bears on is `ungrounded`. Withheld required fields go to the operator.
- The probes are generic ("Company", "From"), and each gets only 3 hits, so the role a field needs may not be among the facts dealt.
- A date the record gives only as a year cannot fill a month field without inventing one, and a figure may come only from dates and figures on record.
- If two groups' fields carry the same label and the same nearby words, they share one question key. On the same page both groups are asked, because every field is routed once, before any is settled (`packages/browser-session/src/core/field-flow.ts:363` `askFields`). The cache, keyed by that text, fills group 2 with group 1's answer only on a later `askFields` — the page asked again, or the next page (`packages/browser-session/src/core/field-routing.ts:34` `withOperatorCache`). Check `fields.json` for `cached: true` on a second group.

### (d) A practice example in the studio

_Setup._ The fixture's sixth row has `origin: practice` — say, a payments platform at Acme, written only to practise on. Each of the five `own` rows also carries one practice highlight, a scale line such as "Size the design for 50,000 requests per second".

1. **Generating.** "Generate prompt" on the practice row, or "Surprise me", which may land on it (`packages/studio-api/src/modules/prompts/prompt-generation.service.ts:168` `leastPractised` has no origin filter). The goal reads `# <title>`, `Where: Acme`, the summary, the stack and the highlights (`packages/studio-api/src/modules/prompts/experience-goal.ts:34` `renderExperienceGoal`). The `design-prompt` run drafts a prompt, its critics check fidelity and label leaks, and the claim saves a `Prompt` with `source: generated`.
2. **Exporting.** Every origin is known, so nothing is refused. `studio-experiences.md` gets the five `own` rows, each without its practice highlight (`packages/memory-ingest/src/core/export-studio.ts:115` `renderExperience`); the practice row is withheld (`packages/memory-ingest/src/core/export-studio.ts:61` `OWN_RECORD`). The report line reads `…/studio-experiences.md: 5 records · 1 withheld as practice`. In `studio-star-stories.md`, stories drawn from an `own` row or from no row are kept, and stories drawn from the practice row are withheld.
3. **Ingesting.** `--kind notes --scope subject --date <export day>` sends only the five `own` rows through Flow A, and every memory takes the declared scope `subject`.
4. **What would go wrong.** A database migrated but not seeded reads every row as `practice`: the export keeps nothing and deletes the earlier `studio-experiences.md`. A scale line left in `highlights` would be exported, and then stored, as attested. A story drawn from the practice row whose experience is later deleted becomes drawn from none, and is kept.
