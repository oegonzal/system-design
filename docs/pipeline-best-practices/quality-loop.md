# The quality loop (`packages/quality-loop`)

The generic quality-control loop from [overview.md](./overview.md), as a NestJS starter that runs end to end. A pipeline is data; the model returns categories and ordinals; the deterministic policy owns every number and the final decision; every run writes a dump. The studio grades and coaches through this package too (`system-design-canvas`, `design-prompt`) — it is the doctrine applied to any task, starting with a system-design prompt held in a markdown file.

## The loop, stage by stage

| Doctrine stage                | Here                                                                                                                                                                                                                   |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Define task contract          | `core/stages/derive-criteria.ts`: one structured extraction turns the goal (the md file, verbatim) into criteria classified by the pipeline's kinds. Ids are engine-assigned (`c1`…).                                  |
| Generate artifact             | `core/stages/llm-producer.ts`; or a supplied `output` provided as iteration 1; or a recorded iteration of an earlier run adopted verbatim (`adopt`).                                                                   |
| Deterministic validators      | `core/stages/schema-validator.ts` always first — `schema` blocks on a structural fault, `bounds` warns once per field past its target — plus any `Validator<T>` a pipeline brings. A `block` failure skips every lens. |
| Critics                       | `core/stages/llm-critic.ts`: defects with type, severity, confidence, fixability, location refs and criterion refs — all enum-locked per request.                                                                      |
| Evaluators                    | `core/stages/llm-evaluator.ts`: `pass                                                                                                                                                                                  | partial | fail  | not_applicable` per criterion of its kinds. Each kind has exactly one judge. |
| Evidence normalizer           | `core/evidence/normalize.ts`: admission, structural keys, agreement across samples, lower-middle medians, cross-lens merge, reconciliation.                                                                            |
| Deterministic decision policy | `core/controllers/`: scores, then gates in a fixed order, every step traced.                                                                                                                                           |
| Controller decision           | `accept                                                                                                                                                                                                                | revise  | retry | escalate                                                                     | reject`, plus the runner's stop reason. |
| Trace + lessons               | `core/loop/run-pipeline.ts` returns a `RunTrace`; `dump/build-run-dump.ts` lays it out; `@sysdesign/run-dump` writes it under `static/runs`.                                                                           |

Everything under `src/core/` is pure: no Nest, no filesystem, no clock (`now` is injected). The Nest layer (`src/modules/`) binds the model client, the pipeline registry, the trace store and the run janitor.

## Running it

```bash
# one run from the command line (builds first; the dump path is printed)
pnpm quality-loop:run --pipeline system-design --goal packages/quality-loop/prompts/order-history.md
# judge a supplied artifact instead of producing one
pnpm quality-loop:run --pipeline system-design --goal prompt.md --output answer.json --iterations 1

# the HTTP surface on :3003
pnpm quality-loop:serve
curl -s localhost:3003/pipelines
curl -s localhost:3003/prompts                               # the library: one md file per prompt
curl -s localhost:3003/prompts/order-history                 # { id, title, markdown }
curl -s -X POST localhost:3003/runs -H 'content-type: application/json' \
  -d '{"pipeline":"system-design","goal":"# Prompt …"}'     # 202 { runId }
curl -s localhost:3003/runs/<runId>                          # poll until status is complete

# the service and its web client together (:3003 + :4201)
pnpm quality:start
```

The loop runs on a model or not at all, and only on a Claude Code subscription login. `serve` and `run` ask Claude Code whether it is signed in before Nest boots (a machine login or `CLAUDE_CODE_OAUTH_TOKEN`; an account check, no model call) and exit 1 saying how to get a login; `replay` reads recorded runs and needs none. Only the first-party subscription passes the check (the machine login or the setup-token token); `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and `CLAUDE_CODE_API_KEY_FILE_DESCRIPTOR` are withheld from every Claude Code process, so nothing is billed outside the subscription. The check proves a credential is present, not valid: a revoked token fails the first call, whose recorded exchange carries the CLI's reason. So a run never looks graded when no model ran — the only failure a model can cause at run time is a call that fails (`llm-failed`), which yields no criteria, no artifact or a lost sample, and the controller escalates with no invented number. The dump is still written. The model tier is never optional; the embeddings tier is, and `LlmAvailabilityDto` (`enabled`, `model`, `reason: 'no-key' | null`) describes only that.

`GET /runs/:id` summarises each exchange to `{ scope, ordinal, outcome, durationMs, startedAt }`; the prompts and responses are only in the dump.

**A fixed rubric.** A run that carries `criteria` uses them verbatim and never asks the deriver: the ids are what the caller cites across runs (the studio's prompt keeps `c1…cN` for its life, and every canvas submitted against it is graded on the same list). A rubric that does not fit the pipeline — an empty list, a duplicate id, a kind the task does not declare, more than `maxCriteria`, a statement longer than the pipeline's `maxStatementLength`, which is the longest its own deriver can return (`keptAtMost` of its statement bound: the contract's 400-character bound unless the task declares its own; the experience digest declares 1,200, sized above what its deriver has measurably written) — is refused with 400 before any row exists. One rule for both sides, so any rubric a run derived can be handed back; a supplied statement past the bound's target is an overrun on the run's record, as a derived one is, and boot holds every pipeline's bound under the edge's `MAX_PROVIDED_STATEMENT_LENGTH`, which is sized from the largest bound a pipeline may declare. `POST /criteria` is the derive stage on its own: it answers the rubric, or 503 with the model report and the diagnostic when the model derives none, and never invents a list. `criteriaProvided` on the run record says which happened. The prompt library is a port (`PromptLibrary`) with a filesystem adapter — a database-backed one drops in behind the same routes.

## Memory runs

A memory run is the `memory` orchestrator. `POST /orchestrations/memory` takes exactly the run inputs (`pipeline`, `goal`, `output?`, `maxIterations?` — the last two reach the target only) and composes the three pipelines through the one `RunsService`, as data over the untouched engine (`src/orchestrators/memory/`, its ports bound by `src/modules/memory/`): **recall** turns the goal into up to six condition-shaped probes plus the goal itself, embeds all of them in one batch (cached in `memory_embedding` by model and text hash), searches every probe against both named vectors in one `queryBatch`, fuses the rankings by reciprocal rank to at most 16 chunks, runs `memory-recall` on them and keeps what it admitted — kept chunks no confirmed finding names, strongest support first — appended to the goal under `## Remembered evidence (advisory)` within the goal budget; **target** runs the requested pipeline on that goal; **digest** runs `experience-digest` on the finished target with the bare prompt (the advisory section is stripped, so remembered lessons are never re-digested); **store** writes one point per admitted memory to Qdrant under a deterministic id per (source run, ref) — carrying a `condition` vector of its `appliesWhen` and a `lesson` vector of its `insight` — so re-digesting a run replaces its chunks, in a collection bound to the index generation, the embedding model and the width. Every step carries a closed status and reason (`MEMORY_STEP_REASONS` in contracts): without a key the memory steps skip with `embeddings-disabled` and the target still runs; an empty store skips recall with `store-empty`; a memory pipeline's output is drawn on when its best iteration cleared the artifact, validator and evidence gates and scored at or above its own `acceptAt`, with items a confirmed finding names still excluded one by one (`not-accepted` otherwise). `POST /orchestrations/memory/from-run { runId }` learns from a run that already happened (recall and target `provided-run`); `POST /memory/:id/reindex` re-embeds what a memory run already digested, which is how an index-generation bump is migrated without asking a model to derive the lessons again; `POST /memory/retrieval-report { goal }` answers what a recall would retrieve, running no pipeline; `GET /orchestrations` and `GET /orchestrations/:id` answer from the `orchestration_run` table, whose row holds the step ledger and the availability the run saw, with one `orchestration_run_child` row per child run (each an ordinary run at `GET /runs/:id`). The janitor fails a row whose heartbeat went stale, with no child still heartbeating, and closes its steps as `interrupted`. The store is verified at boot and per run and reported as data, never as a status code. The map-level view — how the three pipelines compose, every closed reason and what to do about it, how to operate it, and what the live runs showed — is [../pipelines/memory-runs.md](../pipelines/memory-runs.md); the orchestrator layer it is one instance of, beside calibration, second opinion and the router, is [../pipelines/orchestrators.md](../pipelines/orchestrators.md).

## Recall for a producer

A run may ask for lessons from earlier runs before it produces: `POST /runs` with `recall: true`. The studio's coach does, on every start (from the draft and from a graded revision); a grade never does, and the coach panel lists what it was handed. It is the memory orchestrator's recall step, shared rather than repeated — `orchestrators/memory/recall/recall-memory.ts` is the one implementation both call: probes, one embedding batch, one search, a `memory-recall` run over the candidates, and the curated pack read back (kept chunks no confirmed finding names, strongest support first). What differs is where the lessons go. The memory orchestrator appends them to the target's goal, which every lens reads; a run's own recall hands them to the engine as `memories`, a producer briefing kind beside `criteria` and `setbacks` (`ProducerBriefing` in contracts). `setbacks` is the loop's own: on the ask after an attempt its judges read and found no better than the best, a producer that declares it is told that attempt's confirmed finding notes, less any the best's remediations already name, under their own heading after what to fix in the best — so it does not write the same thing again. The first judged attempt is the best until one beats it, so the third ask is the earliest a setback can reach: every producer whose loop can reach a third iteration declares it (the canvas coach, the system-design and agentic-design producers), and none whose loop cannot (the prompt writer's stops at two), which the registry spec holds every pipeline to. A producer that declares it consumes `memories` — the canvas coach does — sees them under `# Lessons from earlier runs (advisory)`, with a lead that they are advice and never requirements; the deriver, the critics and the evaluators have no way to receive them (a lens's `consumes` vocabulary refuses them at boot, they are not part of the contract, and the guarantees spec pins the producer as the section's one call site). The engine knows only `AdvisoryMemory { ref, text }`: where a lesson came from is the host's business.

A run that adopts a judged iteration recalls for what is wrong with it, not for the prompt alone. `RunsService.perform` hands the bound recall the adopted iteration and its rubric (`RecallBase`), and `focusOf` (`orchestrators/memory/recall/focus.ts`) reads its ledger: the confirmed findings, worst first, with the words their lens gave them, and the criteria it failed or met in part, fails first — five and three at most, one per lesson the curator may keep (`MAX_FOCUS`). Each becomes a probe of its own, searched beside the goal (`probeSet`: the goal, then the focus, then the derived conditions); the probe deriver is shown the same lines after the goal, under the same heading, so the conditions it writes reach for the situations that produce those defects (`QueryProbes.derive(goal, focus)`); and each is an item of a delimited `## What is wrong now` section of the curator's query, each cited `d1…` the way derived conditions are cited `p1…`, so a candidate says which defect surfaced it. The memory orchestrator's recall passes no focus and is the recall over the goal alone it always was. The recall's record says what it was focused on (`RunRecallDto.focus`, null for a prompt-only recall and for every row older than the focus). The producer is still the only stage handed the kept lessons; the judges never see the focus or the lessons.

It also screens out what its producer already holds. Adopting copies the base's ledger and remediations verbatim, and so did every sibling coach run that adopted the same iteration, so lessons digested from that chain restate what the producer is about to be handed. `RecallBase` carries the base's pipeline and what its run had adopted; `MemoryRunRecall` walks the chain through `RunsService.get` (`recall/lineage.ts`, at most eight links) and builds `RecallKnown` (`recall/known.ts`): the chain, the hash of the bare goal, the base ledger's finding keys and criterion results, and its remediation notes. `recallMemory` then searches three times wider than it offers (`POOL_FACTOR`) and screens the fused pool (`recall/novelty.ts`), first match wins: `chain-iteration` (a chain run's lesson at an iteration no later than the chain's), `sibling-copy` (a lesson whose `lineage.judged` is a link of the chain) and `known-evidence` (same pipeline — and same prompt when its lineage records one — and every cited finding a held key); twins another run digested from the same evidence of one prompt take one slot. `EXCLUSION_POLICY` declares, per reason, whether to exclude or demote. Every offered candidate carries its origin (`chain`, `same-prompt`, `same-pipeline`, `other-pipeline`) on its provenance line, and the curator's query lists the producer's first eight notes under `## Already in hand — do not restate` with a novelty rule beside them; a kept chunk that only restates one is the `restated_defect` finding (precision, not gated), which withholds it once confirmed. A pool the producer holds entirely opens no recall run: `empty`, `nothing-new`. The record says what was screened (`RunRecallDto.novelty`: the chain, the counts, each exclusion with what it matched, each offered lesson's origin; null for a recall that screened nothing and for every row older than the screen). A recall with no base — the memory orchestrator's — searches, composes and records exactly as before.

The run opens at once (202) with `recall: { status: 'recalling' }` — unless it can never call its producer (a supplied output or an adopted iteration with a budget of one iteration, `mayProduce` in contracts), which opens `skipped` with `no-produce-iteration` and recalls nothing, since no other stage could be handed the lessons (`openingRecall`, the one rule the loop and the studio's fake share); `RunsService.perform` recalls before the loop starts, names the `memory-recall` run on the record as soon as it opens — that run is opened as this one's child, so its own row says `parentRunId` (`quality_run.parent_run_id`, a set-null self-reference), and the composition reads both ways as data on `GET /runs/:id`, in each run's `manifest.json` and on the child's `run.md`, and `GET /runs` lists the child with its `parentRunId` too — and publishes the outcome — `recalled` with the lessons, `empty` (`store-empty`, `not-accepted`, `no-usable-memory`, `nothing-new`) or `skipped` (`no-produce-iteration`, `embeddings-disabled`, `store-unavailable`, `pipeline-unavailable`, `embedding-failed`, `query-refused`, `run-failed`, `no-rubric`, `no-artifact`, `recall-unavailable`, `errored`), one table in `RUN_RECALL_REASON_STATUS`. Nothing about a recall can fail the run: whatever it comes to, or throws, is recorded and the loop goes on with what it got. The run record, its row (`quality_run.recall`, jsonb), the list row (without the lessons), the dump (`recall.json`, a `## Recall` section in `run.md`, and the producer's own prompt under `05-llm/`) all carry it, so whether a lesson helped can be audited against the store later. The row is written through the runs module's own port, `RunRecallRecorder` (`modules/runs/recall/run-recall.ts`, bound under `RUN_RECALL_RECORDER` to the same MikroORM adapter), never through the core's `RunRepository`: the engine's ports name no recall contract, and the guarantees spec holds them to it.

Module wiring, and why it has no cycle: the memory module already imports the runs module (it composes pipelines through `RunsService`), so the runs module cannot import it back. The runs module owns an extension slot instead — `RunRecallSlot` under `RUN_RECALL_SLOT`, empty at boot — and the memory module's `MemoryRunRecall` binds itself into it at init. The slot is optional by design: a composition of the runs module without the memory module has nothing bound, and a run there that asks to recall is recorded `skipped` with `recall-unavailable` and goes on (`run-recall.spec.ts` boots exactly that composition). No shipped process is one — the served app and the `run` CLI boot `AppModule`, which binds the recall, and replay boots neither module and starts no run.

## Persistence

Runs persist through MikroORM's EntityManager, in normalized tables: `quality_run` (the header, the live exchange log and the heartbeat the janitor reads), `quality_run_criterion` (the derived contract), `quality_run_iteration` (one row per loop turn), `quality_run_finding` and `quality_run_criterion_result` (the ledger's two lists, each with a denormalised `run_id` for cross-run SQL). The wire record is reassembled exactly from these rows, so `GET /runs/:id` answers the same after a restart; the `RunRepository` port (`core/ports.ts`) is the seam, `modules/runs/persistence/` the MikroORM adapter and the pure mapper. The row is opened before the loop starts, exchanges flush as they are attributed and refresh the heartbeat, and the trace lands in one transaction when the loop ends. The janitor fails a row as `Interrupted` only once its heartbeat is older than `QUALITY_LOOP_RUN_STALE_AFTER_MS`, so a CLI run beside the service is safe, and the owner's late close reclaims a swept row with the true outcome. The dump is unchanged and remains the full audit trail. Migrations live in `packages/db` (`pnpm db:migrate`, `pnpm db:migrate:check`).

Orchestrations add `orchestration_run` (the step ledger above) and `orchestration_run_child` (one row per child run, keyed by step and ordinal); memory adds `memory_embedding` (the cache). The vector store itself is Qdrant (`docker-compose.yml` service `vectors`, named volume `sysdesign-qdrant`), started and stopped with the database by `scripts/stack.sh` — which `tilt up` runs too — and reached through the `MemoryStore` port (`src/modules/memory/ports.ts`) and its adapter under `qdrant/`.

## The dump

`<QUALITY_LOOP_DUMP_DIR>/<runId>-quality/` (default `static/runs`): `manifest.json`, `run.md` (the human entry point), `01-goal.md` (verbatim), `02-contract.json` (the derived criteria), `03-pipeline.json` (the definition as data), `04-iterations/NN/{iteration,artifact,validation,critics,evaluators,ledger,decision,remediations}.json` plus `artifact.md` (the text every judge read, empty when no artifact was produced), `05-llm/NN.<stage>.<ordinal>.{system.txt,user.txt,response.json,meta.json}` (every exchange, attributed by lens and sample, prompts as text so `grep -r` works), `06-lessons.json`, and — for a run that asked to recall — `recall.json`, the recall exactly as the run recorded it, lessons included. One row per run in `index.jsonl` with `kind: 'quality'`. The headline is the iteration the run stands on: `manifest.overall`, the index row's `overall` and `run.md`'s verdict line are the best iteration's, with the last iteration's score in a clause of its own only when the last is not the best. `DUMP_SCHEMA_VERSION` is 2.

What the model seam kept is reported, not hidden. Each exchange's `meta.json` carries its `salvage` — the fields written past their targets with how each was handled (`accepted`, `kept-over-ceiling`, `cut`, `trimmed`), the repairs, the faults of a refused reply, whether the value was read from a cut transcript, and whether the ask named the previous reply's faults — and its `apiCalls`. `manifest.overruns` tallies them (overruns, calls, over the ceiling, cut, trimmed, salvaged, feedback asks) and the index row carries the count. `run.md` lists every such field under `## Overruns` (`call | field | asked | accepted | written | handling`) and names on a call's own line the API calls a resumed turn took, a salvaged transcript and a feedback ask. A recall that screened what its producer held prints its novelty line under `## Recall` — `novelty: pool N → excluded K as already known (by reason) · collapsed C · offered O · chain run@i → …` — each lesson it set aside with what it matched, and each lesson's origin.

## Declaring a pipeline

A folder beside `src/pipelines/system-design/` and one line in `src/pipelines/index.ts`. The core never changes.

- `definition.ts` — the data: `goalSource` (`brief` for a goal a person types, `composed` for one another step builds — a composed pipeline is never a route, an orchestrator's target or a choice in the web client), `criterionKinds` and `findingTypes` (id → one-line meaning shown to the model), `maxCriteria`, the producer and criteria-deriver personas, the lens specs (`id`, `persona`, `samples`, `maxItems`, `maxTokens`; evaluators add the `criterionKinds` they judge), and the `policy`.
- `lenses/*.md` — one markdown persona per lens, imported with `?raw`. The engine's `prompting.ts` adds the rules every lens obeys (cite only listed ids, answer in the schema, be complete and concise); the md says what the lens knows.
- `output.ts` — the only code: a zod `schema` for the artifact, `locate(output)` giving positional ids (`component.2`), `render(output)` printing every id verbatim where a judge reads it, and an optional `normalize(output, contract)` the loop applies to produced artifacts only — before any validator, so what is judged is what is stored; a provided artifact is never touched. When a validator still blocks an iteration, its notes reach the next produce as a refusals section of the briefing.

**Bounds.** Every string and list a model writes into is one declared bound (`@sysdesign/contracts` `bounds.ts`): `bounded.text` / `bounded.list` over `bound(target)`, whose ceiling is the target plus a declared tolerance, `exact(n)` for a cap the engine slices to, and `bounded.id(max)` for an id, which stays strict. The model is shown every target (`modelSchema(schema).json`); a reply is read to the ceilings through `parseLenient`, so a size overrun is kept and recorded and only a structural fault refuses it. Every target and output cap is held to what the model measurably writes: `pnpm measure:bounds [--runs-dir] [--since]` reads the dumps read-only and regenerates `measured.json` beside each module that declares bounds (`pipelines/<id>/`, `core/stages/`, `contracts/lib/measured/`), and the definition specs fail when a target sits below the measured 99th percentile, a ceiling at or below the longest written, or a cap less than a fifth above the most its stage wrote — and when a measured field or stage is gone or a declared one was never measured, unless the spec exempts it with its reason written where the exemption is made. Run it before changing any bound or cap.

`validatePipeline` runs at boot and at every run: weights sum to 1, every kind and type is priced onto a known dimension, thresholds and decay are in range, every lens can reach `minHits`, every kind has exactly one evaluator, no reserved or duplicate ids, and the output schema converts to JSON Schema.

Six instances exist, each a folder under `src/pipelines/`:

| Pipeline               | Artifact                        | Input                                                                                                                                                                     | Criterion kinds                               | Dimensions                                              |
| ---------------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- | ------------------------------------------------------- |
| `system-design`        | `DesignAnswer`                  | a prompt md                                                                                                                                                               | functional, non_functional, scale, constraint | completeness, quality_attributes, compliance, soundness |
| `memory-recall`        | `MemoryPack`                    | a prompt md plus candidate chunks recalled for it (`input.ts`)                                                                                                            | need, admissibility                           | coverage, precision, fidelity                           |

A pipeline whose input is more than a prompt owns an **input codec** (`input.ts`): a typed input rendered to the goal markdown — the flexible md verbatim under its own heading, pipeline-owned sections around it, engine-assigned aliases (`m3`, `f4`, `r2`) — closing with `## Index`, a fenced JSON block the codec reads back with zod. The input schema refuses anything that would render beyond the goal budget. Every alias is a location the artifact must give a verdict to (`kept ∪ dropped`, `evidence ∪ unused`), so a finding about an item keeps its key across revisions and maps straight back to the source. **Exact checks are validators** (`validators.ts`): an alias the index does not hold, an alias placed twice, an item left without a verdict, a pack or digest over its limit — each blocks, none reads prose; both validators start from the output schema because the engine runs every validator on any artifact it has. What the goal does not state cannot become a criterion, so standing rules such as grounding and transfer are critic-checked finding types, and `experience-digest` records the engine's own facts — remediations selected, transitions from the lessons, score deltas — rather than letting a model author an effect.

## How evidence becomes a decision

**Scores.** For each dimension: criteria of the kinds mapped to it earn `resultValues[result] × kindWeight` (`unassessed` earns nothing but keeps its weight); the base is 100 × earned / total. Confirmed, unreconciled findings mapped to the dimension subtract `bySeverity[severity] × confidenceWeights[confidence]`, worst first, each decayed by `decay^position`, the total clamped to `maxPerDimension` pro rata. A dimension with nothing mapped to it is `null` and renormalises out; one with findings but no criteria starts at 100. Overall is the weighted mean of assessed dimensions.

**Gates, in order, each traced even when skipped:** artifact present → blocking validators → evidence sufficient (`minAssessedShare` of criteria assessed) → policy allowed (no finding at a blocking severity or gated type, no gated kind failed; routed by fixability: `unfixable` → reject, `requires_user` → escalate, `requires_retry` → retry, else revise) → `acceptAt` → `rejectBelow` (retry: regenerate rather than edit) → route by remediations (none → escalate; all retry → retry; else revise).

**The loop** revises or retries with the selected remediations, hydrated with the lenses' own words by the runner (the policy never sees prose), keeps the best iteration by a strict-better gate, and stops with `accepted | rejected | escalated | plateau | max-iterations | produce-lost`. A produce that answers nothing is still decided — no artifact, so it escalates — and spends its iteration, and the loop asks again in the same mode from the same best with the schema's faults named, until it has lost more produce calls than `loop.lostProduces`; a lost lens sample scores but cannot gate (`evidence.lostSample: 'score-only'`). An adopted iteration is iteration 1 verbatim, in mode `adopted`, and no stage runs for it.

## The web client (`packages/quality-loop-ui`)

One screen on :4201 (`pnpm quality:start` serves both): pick a prompt from the library and a pipeline from `GET /pipelines`, choose the iterations (default 1 — a live iteration is minutes), run. While the loop runs the page follows `GET /runs/:id` by the run's own status and lists each model exchange as it is attributed; when it ends it shows, per iteration, the decision with its gates and reason, the overall and per-dimension scores, the criteria joined to the contract, the confirmed findings grouped by severity with the remediation notes the policy selected, how the policy decided step by step, and the rendered artifact with its `[component.N]` ids. The prompt and the artifact display as text — no markdown renderer, so the ids a finding points at stay visible.

A "Recent runs" panel lists what the service has persisted, newest first; clicking one reopens it, and the run being shown lands in the URL as `?run=<id>`, so a reload or a bookmark brings it back for analysis.

The client renders the wire contract and nothing else; it shares the request core and polling hook with the studio through `@sysdesign/web-kit` and the spec harness through `@sysdesign/web-testing`.

Not built yet, by choice: response memoisation (ENG-7), per-iteration streaming to the client while the loop is running (the trace lands when it ends; ENG-6), storing findings and sections as memory chunks (an ingester over the same store), a web-client control for memory runs, a human review queue (PLAT-8).
