# memory-ingest

The user's documents — a PDF résumé, markdown notes, the studio's own record of their experience exported as documents — chunked deterministically and handed, one chunk at a time, to a store that digests each into facts about the subject and keeps them: the quality loop's `document-memory` orchestrator, or a memory space on the memory host (`packages/agentic-system`, `/spaces`), chosen by `MEMORY_INGEST_SINK`. A Node command line over `@sysdesign/loop-client` and `@sysdesign/agentic-memory-client`: no framework, no database, no embeddings here — HTTP to the loop, the memory host and the studio, and one JSON manifest on disk. The same command line reads a space back for its owner: `recall`, `history` and `forget`.

```bash
pnpm memory-ingest ingest notes.md --subject "Ada Lovelace" --dry-run   # print the chunks; post nothing
pnpm memory-ingest ingest notes.md --subject "Ada Lovelace"             # post each chunk, await it, record it; then retract what the document's other digests stored
pnpm memory-ingest ingest Resume.pdf --kind resume                      # subject from MEMORY_INGEST_SUBJECT
pnpm memory-ingest ingest notes.md --force                              # post again what the manifest covers, then retract the earlier digests
pnpm memory-ingest ingest answers.md --scope subject                    # in the loop's store, every memory the document states is the subject's, wherever asked
MEMORY_INGEST_SINK=space MEMORY_TENANT=verify-1 MEMORY_SPACE_NAME=job-assistant MEMORY_INGEST_REGISTERS=profile_fact,profile_story,claim_boundary \
  pnpm memory-ingest ingest Resume.pdf --kind resume                    # the same, into a memory space, under the tenant alone
pnpm memory-ingest retract Resume.pdf --dry-run                         # the digest runs the manifest names for a document through the configured store; retract nothing
pnpm memory-ingest retract Resume.pdf                                   # retire a document from that store: retract every digest run its entries name, and mark them
pnpm memory-ingest status                                               # the manifest, as a table — every posting, through either store
pnpm memory-ingest status --refresh                                     # re-read every posting made through the configured store from its service
pnpm memory-ingest export-studio --out docs/ingestion/studio            # the subject's own experience profiles and STAR stories, as markdown to ingest; practice withheld
pnpm memory-ingest recall --space job-assistant --tenant verify-1 --text "years of experience with Postgres"   # what the space holds for the tenant, by meaning
pnpm memory-ingest recall --space job-assistant --tenant verify-1 --key "Ada Lovelace" --register profile_fact  # by a key a record holds, in one register
pnpm memory-ingest recall --space job-assistant --tenant verify-1 --under project=job-assistant --text "notice period"   # … narrowed by the keys an agent wrote under, so its taught answers are reached
pnpm memory-ingest history <recordId> --space job-assistant --tenant verify-1 [--under project=job-assistant,unit=<hash>]   # every version of one record, oldest first
pnpm memory-ingest forget <recordId> --space job-assistant --tenant verify-1 --reason "stated of someone else"  # close one record, the reason kept on it
pnpm exec nx test memory-ingest                                         # one pure vitest project; the in-repo fakes and the runtime's in-process engine, never a live service
```

Exit codes: `0` ok — every chunk is covered (below): its facts are in the store, now or from before, or it holds none to store; and every digest run the command set out to retract is retracted, now or before; `1` a chunk failed, the store refused one, or the digest settled one with its facts left out of the store (`unstored`, below), or a retraction the store did not carry out left a digest run standing; `2` a usage problem or an input the program cannot use (an extension no reader takes, a missing file, a part the budget cannot hold, a subject or file name past the contract's bound, more parts per chunk than the configured store's digest takes), a store that cannot serve the run (a space nobody holds under the name, one that does not take the configured registers), a path `retract` finds no manifest entry for through the configured store (the message names the manifest and the store), a manifest home another command is writing (the message names its lock file), or what a space command could not do — a space nobody holds, a record the tenant's scope does not see, a host that did not answer.

## Environment

| ------------------------- | --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `MEMORY_INGEST_SINK`      | `loop`                      | Which store the documents are posted to and every manifest command acts on: `loop` or `space`.                                                          |

| `MEMORY_SPACE_NAME`       | `none`                      | The space the space sink posts to, by the name it was ensured under. Required, by name, when the sink is `space`.                                       |
| `MEMORY_INGEST_REGISTERS` | `none`                      | The registers a digest may file into, comma-separated; each must exist on the space and take a `remember`. Required, by name, when the sink is `space`. |
| `STUDIO_API_URL`          | `http://localhost:3000/api` | The studio API's base URL, its prefix included, read by `export-studio`; must be `http(s)`.                                                             |
| `MEMORY_INGEST_HOME`      | `static/memory-ingest`      | Where `manifest.json` lives, relative to the working directory.                                                                                         |
| `MEMORY_INGEST_SUBJECT`   | —                           | Whom the facts are about, when `--subject` is not given on the command.                                                                                 |

Flags and variables are declared once, as data, in `src/config.ts` (`INGEST_FLAGS`, `INGEST_ENV`); each flag's value is read in `src/flag-values.ts`; a value that cannot be used is refused by name, and the usage prints each flag's meaning from its declaration. Under the loop sink the three space variables are not read.

## How a document becomes chunks

`src/core/chunk.ts`, pure. Readers (`src/adapters/readers/`, a declared table by extension: `.pdf` through the PDF engine's positioned text items, cut into blocks by the page's own geometry — a gap larger than 1.5× the page's median line pitch or a change of type size opens a block (`src/adapters/readers/pdf-blocks.ts`) — with the pages joined by form feeds; `.md`, `.markdown`, `.txt` verbatim) hand over text; the chunker reads its structure: a heading line, a list item with the lines that continue it, and a blank-line paragraph each become one **part**. A part past the contract's cap (`DOCUMENT_PART_MAX_LENGTH`) is split at the last whitespace before it. Parts are packed greedily into chunks whose rendered goal (`renderDocumentGoal`) stays under `--chunk-bytes` (default 6000) and whose part count stays under `--parts-per-chunk` (default `PARTS_PER_CHUNK`, 8: measured so the loop's 16 memories can hold two facts per part; at most 16 for a space, whose register digest takes no more sections — `PARTS_PER_CHUNK_BOUND`). **Nothing is repeated between chunks** — a store cannot dedupe a near-duplicate fact — so continuity comes from `context`, the headings enclosing the chunk's first part. `maxMemories` is always the contract's `DOCUMENT_MAX_MEMORIES`: a dense part states several facts. A chunk's `chunkHash` is the sha256 of its rendered goal, and the goal carries more than the chunk's sections: the file's name as its title, the kind, the subject, the date (`Undated` without one), the chunk's place (`Chunk i of n`), the headings it sits under, the rules, and — only when `--scope` declares one — the scope every memory of the document takes, in place of the scope test among the rules. So the same text yields the same chunks and hashes only under the same file name, flags and rules, and a document that declares no scope hashes exactly as before scopes could be declared. An edit that keeps the chunk count, the packing and the headings changes only the hashes of the chunks it touched; one that changes the chunk count, or a new `--date`, `--scope`, subject, kind or rules, changes every hash in the document. `--scope` takes only a scope bound to no unit of work (`subject`): a file names no unit, and a memory bound to one is read only for the unit it was recorded for, so a document that declares none has any memory its loop digest scopes to a unit withheld rather than stored unread — and the chunk reads `unstored`, holding the document's replacement back (below). A space writes every memory under the tenant whatever `--scope` says.

## Two stores, one manifest

A chunk is posted through the configured **sink** (`src/core/ports.ts`, `IngestSink`), and the manifest records the **store** it went to: the sink, `loop` or `space`, and for a space the space it went to and the scope it wrote under — the tenant's partition. A store is one copy of a document's facts, so **every manifest command acts on the postings made through the configured store alone** (`sameStore` in `src/core/record.ts`): a chunk is covered, a document replaced or retired, and a status refreshed within one store; every other store's postings — the other sink's, another space's, another tenant's in the same space — are listed by `status` and otherwise kept as they are. A document already in the loop's store is posted whole to a space, and replacing it there retracts nothing the loop holds; a document seeded into a space under one tenant (`MEMORY_TENANT=verify-1`) is posted whole again under another (`MEMORY_TENANT=<the live one>`) from the same manifest home, and retiring or replacing it under one tenant touches nothing of the other's. Retiring a document from the loop is `MEMORY_INGEST_SINK=loop memory-ingest retract <path>`, from a space `MEMORY_INGEST_SINK=space MEMORY_TENANT=<tenant> MEMORY_SPACE_NAME=<name> …`. That is what lets a store be filled and verified beside the one still in use, and the old one retired afterwards, make before break.

**The loop** (`src/adapters/loop-http/`): the chunk's rendered goal starts one `document-memory` orchestration, awaited to settle by heartbeat through `awaitOrchestration`; its `digest` and `store` steps are the manifest's two phases, and what it stored is named by the digest step's child run — the id every point it stored carries — which is what a retraction names (`DELETE /memory/:id`).

**A space** (`src/adapters/space-http/`): checked once at boot (`resolveIngestSpace`) — the space under `MEMORY_SPACE_NAME` exists and compiles, declares a partition, and every register in `MEMORY_INGEST_REGISTERS` exists and takes a `remember`, every unmet need listed in one refusal — the chunk is handed to the host as one register digest (`POST /spaces/:id/digests`): its parts as the sections, each labelled by the headings above the chunk; the ingest's own rules in the register digest's words (`INGEST_RULES` in `digest-request.ts`: one fact per memory, a predicate a form could ask by, a value a field could take, qualifiers kept, the subject named and the document's date stated — and no scope test, because the scope is declared); the configured registers; the scope of the tenant's partition alone (`{ <partition>: MEMORY_TENANT }`), never a project or a unit, so every agent of the tenant reads what a document states; and provenance `memory-ingest:<kind>` with the chunk's hash as the source run, so a record says which chunk it came from and a re-posting of the same text is the same source. The sink then reads the digest back (`GET /spaces/:id/digests/:runId`) every `DIGEST_POLL_EVERY_MS` until the loop settles it — a digest has no heartbeat of its own; the loop's janitor fails a run whose beat has stopped, so the wait ends however the digest settles — applies once what its step endorsed (`POST …/remember`; a digest the host says is applied already is read back, and the host's record of that apply is the answer), and records the record ids the apply answered on the entry. The store phase is the sink's own, with its own declared reasons (`STORE_STEP_REASONS`): `nothing-endorsed` when the digest left nothing to apply (its own step says why — `no-memories`, `not-accepted`, …), `not-applied` when a digest settled with memories to apply and the apply never happened (the wait was lost; `status --refresh` reads it back, and the next `ingest` posts the chunk again), `items-refused` when the runtime refused one or more endorsed memories (the rest are kept; the chunk is not covered). Retracting a space posting invalidates each recorded record with the reason `retracted by memory-ingest` (`RETRACTION_REASON`; `history` shows it), under the scope the posting wrote under, every refusal collected rather than stopping at the first — a record closed already counts for nothing — and the batch refused as a whole when any was, so the posting stays unmarked and a later retraction asks again for what is left. A record another standing posting through the store lists too — a fact the space answered `unchanged` when a chunk was posted again, so the new posting lists the earlier posting's record — is kept current, never closed under the earlier posting's retraction: the posting that still covers the chunk stands on it, and the report counts such records per run (`kept current, listed by a standing posting too`).

## The manifest and what idempotency means

`static/memory-ingest/manifest.json` (gitignored) is written atomically — a temp name, then a rename — after every posting and after every retraction, so a process killed mid-run leaves the previous manifest whole, and no retraction goes unmarked behind a posting's minutes. It is a ledger: every outcome in order, one entry per posting, under `"version": 4`. Version 1 was written before retractions were marked, 2 before a posting could go anywhere but the loop: both are read as loop postings — version 1 with every posting standing — under the URL each recorded; 3 was written before a space posting recorded the scope it wrote under, so its space postings read under no scope — which no store matches, so they are listed and acted on by no command — rather than under a tenant they may not have been written under; every earlier version is saved as 4, and a build that reads only an earlier version refuses a later one by its version rather than drop what it does not know.

```jsonc
{
  "chunkHash": "…sha256 of the goal…",
  "document": "notes.md", // relative to the working directory
  "chunk": { "index": 2, "of": 5 },
  "kind": "notes",
  "sink": "space", // loop | space — which store the chunk was posted to
  "host": "http://localhost:3007", // the service the posting went through
  "spaceId": "…", // the space it went to; null for a loop posting
  "scope": { "tenant": "verify-1" }, // the scope a space posting wrote under — what tells one tenant's postings from another's; null for a loop posting
  "orchestrationRunId": "…", // the document-memory run, or the space's digest run; null when the start was refused
  "digestRunId": "…", // the digest step's child run — the id the loop's stored points carry, or the register digest a space applied
  "recordIds": ["…", "…"], // the records a space posting left current, as its apply answered them; empty for a loop posting
  "status": "complete", // complete | unstored | failed | refused — earned by the store step, below
  "steps": {
    "digest": {
      "status": "complete",
      "reason": null,
      "note": null,
      "counts": { "memories": 4, "endorsed": 4, "withheld": 0 },
    },
    "store": {
      "status": "complete",
      "reason": null,
      "note": null,
      "counts": { "items": 4, "inserted": 4, "unchanged": 0, "superseded": 0, "refused": 0 },
    },
  },
  "error": null, // why a failed or refused posting ended that way; an unstored one is explained by its steps
  "ingestedAt": "2026-10-02T12:00:00.000Z",
  "retractedAt": null, // when what the posting stored was retracted — replaced, or the document retired; null while it stands
  "retractedPoints": null, // how many memories that retraction removed — 0 when the store held none of them by then
}
```

A chunk is identified by its document, its hash and the store it went to, and its **status is earned by the store step**, never read off the run's own: the loop's runner marks an orchestration `complete` whenever no step failed, so a digest skipped because embeddings were disabled, judged and `not-accepted`, or finding `no-memories`, and a store that was `store-unavailable`, all settle `complete` with nothing stored — and a space digest that endorsed nothing settles the same way. The manifest records each of those as `unstored`, with the step's `reason` and `note` saying which; `complete` means what the digest endorsed is in the store — every fact of the chunk, unless a step gives a reason all the same: `unit-unnamed`, a loop digest that bound memories to a unit of work in a document that names none and withheld them; `items-refused`, a space apply the runtime refused a memory of. Which reasons mean the chunk holds no fact to store is declared as data, keyed by both digesting orchestrators' reasons and the store step's own (`HOLDS_NO_FACTS` in `src/core/record.ts`): `no-memories` — a digest judged and accepted that endorsed nothing — and no other. Such a posting stays `unstored` in the manifest, the report counts it `no-facts`, and it covers its chunk as a stored one does; every other reason leaves the chunk's facts out of the store — a `complete` posting's included (`leftFactsOut`), which the report counts `unstored` and names the reason of.

A posting **covers** its chunk when it carries no retraction mark and is `complete` with no fact left out, or `unstored` for a reason that says the chunk holds no fact to store. A re-run **skips** a chunk whose document's latest posting of it through the configured sink covers it and posts everything else — an `unstored` one whose facts are missing, a `failed` one (the service was unreachable, the run failed or was lost mid-wait) and a retracted one are tried again; `--force` posts even the covered ones. A document reads only its own postings, so the same path given twice in one run is posted once, while the same text in two documents is posted once per document — even two files of one name in different directories, whose goals are identical: each document stands on digests of its own, and replacing or retiring one never retracts a fact another stands on. A refusal (`400` for a goal the service would not take, `404` for an orchestrator it lacks, `422` for a digest the space will not write) **stops the run**, since the next chunk would be refused the same way, and so does a start the service is still unreachable for once the client's recovery window has passed (below); the chunks after it are reported `pending`.

A document's digests follow its current text, **make before break**: once every chunk of the document's current plan is covered — posted in this run, or skipped for a posting of its own that stands — every other digest run its entries through the configured sink name is retracted and its entries marked, each mark saved before the next retraction is asked. That is retirement's rule (below) less the runs the plan stands on: a posting that failed after its digest stored, or one settled `unstored` that still names the run that judged it, goes with the rest, and a run already marked is not asked again. So an edit that keeps the chunks' hashes (above) posts only the chunks it touched and then retracts the digests they replaced, and one that renames every chunk — a new chunk count or `--date` among them — posts the whole document again and then retracts every earlier digest of it; `--force` does the same for unchanged text; and a document the run did not cover whole — halted by `--limit` or an interrupt, a chunk refused, failed, or settled with its facts out of the store, none stored or some withheld — retracts nothing, so the store is never left without the document. A chunk that stored the rest of its facts is posted again by the next run, its partial digest standing beside the earlier ones until a run covers the document whole and retracts them all. Its report then says **what held the replacement back**: the first chunk not covered, and how many earlier digest runs outside the current plan still stand — recorded before the run and not marked, the runs the replacement retracts once a run covers every chunk (printed when any does); and it counts the document's entries whose wait was lost after the start, whose digest run no replacement can retract until `status --refresh` reads it back. Replacement goes by the document and not by the chunk hash, because a change to the goal's rules renames every chunk at once. A forced run that halts names both ways on. Re-running **without** `--force` posts only what is not covered yet: it skips what the forced run posted, and it skips the chunks the forced run did not reach too, so those keep their earlier digests, and only the chunks the forced run posted again are replaced. Re-running **with** `--force` posts the whole document again, the chunks the halted run posted included, and then retracts every earlier digest of it. A retraction the store does not carry out ends that document's replacement, the runs after it left standing and said why (exit 1); the next run that covers the document whole retracts them. A document that read as no text replaces nothing — retiring one is `retract`'s. `status --refresh` re-reads every posting made through the configured sink and rewrites the settled ones by the same rule — a space posting's record ids read back from the host's own record of the apply — keeping each entry's retraction mark: the loop still reports an orchestration whose points were retracted as having stored them.

`retract <path…>` **retires** documents from the configured store: every digest run any of a document's entries through that sink names, whatever its status — retracting a run that stored nothing removes nothing — is retracted and marked; a run whose every entry already carries a mark is not asked again. A document is found by the key `ingest` records it under — its path relative to the working directory — and is never read, so one since deleted retires the same; a path the manifest holds no entry for through the sink refuses the command, naming the manifest and the sink, before anything is retracted: run it from the directory, under the `MEMORY_INGEST_HOME` and with the `MEMORY_INGEST_SINK` the document was ingested with. The report gives the memories each run removed, lists the runs that removed none apart, and counts the entries naming a run whose report was never read (a wait lost after the start), whose digest run `status --refresh` reads back before a second `retract`. Every retraction goes through the configured service (`QUALITY_LOOP_URL` or `AGENTIC_SYSTEM_URL`); a run whose posting was recorded under another service of the same kind — every entry keeps its `host` — is retracted and marked all the same, since two services may share one store, but the report lists it apart, `recorded under <url>, retracted through <configured>`, with the memories the configured service's store removed, never among the runs that held nothing. Replacing a document reports the same way.

One command writes a manifest home at a time: `ingest`, `retract` (neither under `--dry-run`, which saves nothing) and `status --refresh` create `manifest.lock` beside the manifest, exclusively, and remove it when they end — on an interrupt or an uncaught fault too. A home whose lock exists is refused, exit 2, naming the file; only a process killed outright leaves one behind, to be deleted by hand once nothing runs. The space commands touch no manifest and take no lock.

Posting is sequential on purpose: one digest at a time, awaited to its end before the next starts, so no store is asked to digest two chunks of one document at once. Every call rides out a restarting service within `INGEST_RECOVERY` (`src/config.ts`): a call that never reached it, or a read it answered with a server error, is asked again every 2 s for 60 s — ten times the six seconds within which each of fifteen watch-mode restarts of the loop, measured on 2026-10-10, listened again — and a start still unreachable past the window stops the run, since every chunk after it would wait the window out too. The sinks speak one vocabulary to the core (`SinkFault`): `refused` and `unreachable` stop the run, `timeout` and a posting `unfinished` after its start do not, and the record keeps the run's id either way.

## The space commands

`recall`, `history` and `forget` are the owner's way to read and correct what a space holds without a curl, each addressing the space by the name it was ensured under (`--space`) and one tenant's partition (`--tenant`), as the ingester writes — narrowed, with `--under key=value,…`, by the keys an agent wrote under beyond it, each one the space declares after its partition (`project=job-assistant`, `unit=<the unit key's sha256>`), since a record is seen only by a scope that names every key it was written under: without `--under` a taught answer kept under the assistant's project is `record.not_found` to `history` and `forget`, and absent from `recall`; a key the space does not narrow by, or the partition itself, is refused by name. `recall` asks the space what it holds for a key a record carries exactly (`--key`, a fact's subject) or for a question matched by meaning (`--text`), narrowed to one register with `--register`, and prints each memory ranked with its register and the day it holds from, then the routes that reached them and what the space's recall budget left out; `history <recordId>` prints every version of a record oldest first, with how each ended; `forget <recordId> --reason "<why>"` closes the current record with the reason, which `history` shows and a later recall omits. `--json` prints the host's records untouched. A name no space holds, a key the space does not narrow by, a record the scope does not see or that is closed already, and a host that did not answer are said and exit 2.

## The studio's record, as documents

The studio keeps the experience profiles its prompts are drawn from and the STAR stories in its own tables, which this package may not read: the boundaries forbid `memory-ingest → db`, and the one program that posts documents is this one. So the record crosses as documents. `export-studio --out <dir>` reads `GET /experiences` and `GET /star-stories` whole — page by page at the API's largest page — and writes one markdown file per source through a declared field map (`STUDIO_SOURCES` in `src/core/export-studio.ts`), every record decided by one rule over its origin — an experience by its own `origin`, a story by that of the experience it was drawn from — and kept when that origin is `own`, or when a story was drawn from no experience, which the studio holds as the subject's. An experience is `# <title> — <company>`, its summary, `Stack: …` and its highlights as bullets; a story is `# <title>` with `## Situation`, `## Task`, `## Action` and `## Result` as its own sections and `Tags: …`, so a chunk's context names which part a fact came from and a `profile_story` can cite the part whole. What the studio keeps only for practice is never written: an example written for practice (`origin` `practice`) and a story drawn from one are withheld and counted under that origin (a line such as `5 records · 1 withheld as practice`), and an experience's `practiceHighlights` — lines it carries only so a prompt drawn from it has them — are never rendered. A record whose origin is not known — an experience whose origin this build does not know, or that has none (a studio older than origins), or a story drawn from an experience the studio did not serve — is refused by name, exit 2, before anything is written. A source left with none of the subject's records writes nothing — an empty document is nothing to ingest — and removes the document an earlier export left at its path, so a stale one is never ingested again. Then name each file you ingest: `ingest <dir>/studio-experiences.md --kind notes --scope subject --date <the day you exported>`, since `--scope subject` states every record in the file as the subject's wherever a form asks in the loop's store (a space writes under the tenant regardless); ingest `studio-star-stories.md` the same way only once every story in it is the subject's — a story drawn from no experience is written as theirs, one saved trying the studio out among them. The manifest skips what was ingested before, and after a change to the record the same command, date and all, posts the chunks the change touched and then retracts the digests they replaced — a new `--date` renames every chunk, so each document is posted whole again. Another source is another entry in the map, never different code.

## Layout

`src/core` (pure — ports, the chunker, the ingest and its report, the record of a posting with its retraction mark and the reasons that cover a chunk with no fact to store, the retraction both paths share and the retirement of a document, the status refresh, the studio export and its field map) · `src/adapters/readers` (the table, PDF, markdown, JSON Lines) · `src/adapters/loop-http` (the loop sink over `LoopClient`) · `src/adapters/space-http` (the space sink over `MemoryClient`: the space checked at boot, the digest request, the digest read as an outcome, and the space by name the commands share) · `src/adapters/studio-http` (the studio's lists, paged) · `src/adapters/fs-ledger` (the manifest, by version, and its lock) · `src/adapters/fs-writer` (the exported documents) · `src/config.ts` and `src/flag-values.ts`, `src/cli.ts` (argv, the lock, the wiring), `src/commands.ts` (what every command is given), `src/manifest-commands.ts`, `src/space-commands.ts`, `src/render.ts`, `src/main.ts` · `src/test` (the port fakes, the shared fake loop behind the loop sink, the scripted memory host behind the space sink's digests, and the harnesses the ingest and CLI specs share — spec code only, outside the app build; what a space does with a record is proved against the runtime's engine through `@sysdesign/agentic-memory-client/testing`). The goal codecs and the chunk schema are `@sysdesign/contracts` (`lib/quality-loop/document-digest.ts`, `lib/agentic-system/register-digest.ts`); the orchestrators are `packages/quality-loop/src/orchestrators/document-memory` and `register-memory`.
