# tool-session

A mission run as tool calls the quality loop decides, for any program that declares tools — the mailbox service, the calendar service, the next one. The program defines its tools (`defineTool`: a name, what it does, zod parameters, an effect, whether a person approves each call, and what runs), ships one settings file, and mounts `ToolSessionModule`; everything else is here.

How a session runs: the rubric is derived once from the mission (`POST /criteria` on the `tool-step` pipeline), then per step the session composes the goal — the mission, the tools, what earlier calls returned, what was just done, what refused the plans before, where the mission stands, the limits, and the index the loop's validators read — asks the loop for one plan, reads it back by the contracts' routing (`routeToolPlan`), runs the executable prefix in order, asks the operator before a call its tool declares approval for and before the question a plan ends on, and ends on the mission's declared stop cause when a plan finishes. The engine adds only declared rails (`config/session/*.json`: steps, minutes, refused plans, failed calls, loop faults) and the operator's say.

Layout: `src/catalog` (a tool, the catalog by name, another program's tools over its `GET /tools` + `POST /tools/:name`), `src/session` (the loop, the rails, what the operator is asked, the registry that runs sessions in memory, the bus adapters), `src/nest` (`ToolSessionModule.register`, `POST /sessions` · `GET /sessions` · `GET /sessions/:id` · `POST /sessions/:id/stop` · `GET /tools` · `POST /tools/:name`), `src/cli` (`run --goal <file>`), `src/settings.ts` (the schema of a program's `config/session/*.json`). The fakes a program's specs take: `@sysdesign/tool-session/testing`.

What a session says on the bus: `tool-session.started`, `tool-session.stepped`, `tool-session.finished`, under the program's own source, and one notice when it ends; a question or an approval is an interaction prompt the channel carrying that source delivers.
