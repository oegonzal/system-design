# google-kit

What a program needs to act as the owner on a Google API, and nothing of any API itself: the credentials it reads (`GOOGLE_ENV`, read from the environment a program's own `config.ts` hands in), the scopes each program needs as one table (`GOOGLE_SCOPES`, requested whole by one consent), the consent that obtains a refresh token (`authorize`: a loopback listener on the declared port, the consent URL announced, the code exchanged), the file that keeps it (`static/google/oauth-token.json`, mode 0600, ignored by git), the access tokens minted from it (`GoogleAuth`), and the authorized request (`googleRequest`: bearer, schema-parsed answer, one re-mint after a 401, a rate limit or a server error ridden out within the declared recovery, any other refusal named by Google's own reason). No dependency: Google's REST APIs are called with `fetch`.

Setting it up, once: in the Google Cloud console make a project, enable the Gmail API and the Google Calendar API, configure the OAuth consent screen (External; add your own account as a test user; set the publishing status to _In production_ so the refresh token does not expire after seven days as Testing-mode tokens do — the "unverified app" interstitial is expected for personal use), create an OAuth client of type _Desktop app_, put its id and secret in `.env` as `GOOGLE_OAUTH_CLIENT_ID` and `GOOGLE_OAUTH_CLIENT_SECRET`, then run `pnpm gmail authorize` (or `pnpm google-calendar authorize`: either requests every scope) and open the URL it prints. A pod with no file reads the token from `GOOGLE_OAUTH_REFRESH_TOKEN` instead.

The fakes a program's specs take — a fetch that answers by route and remembers every call, a token source that mints nothing, Google's own answer shapes — are `@sysdesign/google-kit/testing`.
