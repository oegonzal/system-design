# quality-loop

The generic critic → evaluator → controller loop as a NestJS service. Pipelines are data (vocabularies, md lens personas, a decision policy) plus one `OutputShape`; models return enums and ordinals; the deterministic policy owns every number and the final decision; every run writes a dump and a row.

```bash
pnpm quality-loop:run --pipeline system-design --goal packages/quality-loop/prompts/system/order-history.md
pnpm quality-loop:serve          # the HTTP surface on :3003 (QUALITY_LOOP_PORT)
node packages/quality-loop/dist/main.js replay --pipeline system-design   # every recorded iteration, decided again by each controller
pnpm memory:import-qdrant --collection quality-memory__v2__text-embedding-3-small__1536   # once: the memory collection carried over from the Qdrant that held it
pnpm exec nx test quality-loop
```

Layout: `src/core` (the pure engine — `contracts/`, `stages/`, `evidence/`, `loop/`, `outputs/`, `controllers/`, `testing/`; `pipeline.ts`, `policy.ts` and `ports.ts` are its interface), `src/pipelines/<id>` (one folder per pipeline: `system-design`, `agentic-design`, `memory-recall`, `experience-digest`, `knowledge-digest`, `document-digest`, the browser session's three — `browser-step`, `field-answer`, `answer-suggestions` — and `tool-step`, one plan of tool calls over whatever tools a program declares, and the studio's two — `system-design-canvas`, a drawn canvas judged or coached, and `design-prompt`, a prompt written from an experience), `src/orchestrators/<id>` (`memory`, `knowledge`, `router`, `calibration`, `second-opinion`, `form-memory`, `document-memory`, each data over registered pipelines; `runner/` sequences and records them, `panel/` and `common.ts` hold what two of them share), `src/modules` (Nest wiring: `runs`, `orchestration`, `memory`, `router`, `prompts`, with `http/` the one edge the controllers share), `src/cli` (`run`, `replay`, `import-qdrant`), `src/dump` (the run-dump layout), `prompts/` (the library `GET /prompts` serves; one markdown file per prompt, titled by its H1).

The memory store moved from Qdrant to pgvector on 2026-11-12. `pnpm memory:import-qdrant [--from <url>] [--collection <name>] [--dry-run] [--force]` (`main.js import-qdrant`) carries a collection over once: it scrolls every point of the named collection from the Qdrant at `--from` (default `http://localhost:6333`) with its payload and both named vectors, and upserts each into the store's table under the id it had — `memory_support.point_id` names those ids — keeping `storedAt` as written. A point whose id is not its run and ref's, whose payload the store does not write, or whose vector is missing or not the store's width is refused by name and the rest are written; the command prints `scanned`, `imported`, `refused`, the first refusal and the time taken, and exits 1 on any refusal unless `--dry-run`, which checks every point and writes nothing — not even the table, which the service makes at boot: one not there yet is read as holding nothing. A flag the command does not know exits 2 with the usage line. `--collection` defaults to the configured embedding client's collection and is required without `OPENAI_API_KEY` — the name says the model and the width, and a collection of another store or generation is refused. Run it once, after `pnpm db:migrate`, with the quality loop stopped, before the loop runs on pgvector and before the old `sysdesign-vectors` container is removed: the compose `vectors` service is gone, and what still serves :6333 is that leftover container — `docker start sysdesign-vectors` if it was stopped, and once it is removed `docker run --rm -d -p 127.0.0.1:6333:6333 -v system-design-prep_sysdesign-qdrant:/qdrant/storage qdrant/qdrant:v1.19.1` serves the retained volume again. The import is for a store the loop has not written to since the move: it only adds and replaces by id, so run over a table the loop has worked on it would bring back the refs the loop has since replaced — a table that already holds chunks is refused unless `--force` is given. Measured 2026-11-11 on the laptop's collection: 1,455 points in 14.7 s into an empty table, 8.2 s run again (what `--force` does now), 1.4 s dry; the five nearest to a stored vector agreed with Qdrant on ids and on scores to four decimals.

How it works, the env variables, the dump layout and the guarantees: [docs/pipeline-best-practices/quality-loop.md](../../docs/pipeline-best-practices/quality-loop.md); the orchestrators: [docs/pipelines/orchestrators.md](../../docs/pipelines/orchestrators.md).

Runs persist in Postgres through MikroORM (`pnpm stack:db` then `pnpm db:migrate`, on the default port 5433); the memory store is a pgvector table in the same database (`vec_quality_memory__v2__<model>__<dims>`: the `vector` extension arrives with `pnpm db:migrate`, the table and its indexes at boot, bound to the embedding model `OPENAI_API_KEY` enables). HTTP: `GET /health` (with the model that backs the loop and the pace its runs heartbeat at: `heartbeatEveryMs`, `staleAfterMs`), `GET /pipelines`, `POST /criteria` (a pipeline's rubric for a goal, no run), `POST /runs` (202; `criteria` fixes the rubric, `output` provides the artifact), `GET /runs`, `GET /runs/:id`, `GET /runs/:id/dump` and `GET /runs/:id/dump/*path` (a run's dump: its files, then one of them), `GET /prompts`, `GET /prompts/:id`, `POST /orchestrations/:orchestrator` (202; `memory` recalls → runs the target → digests → stores, `knowledge` learns from a finished run — what the store knows → a typed digest → items, findings and reinforcement, `router` classifies the brief and runs the judge it picks, `calibration` and `second-opinion` run a panel), `POST /orchestrations/:orchestrator/from-run` (202; start from a persisted run), `GET /orchestrations`, `GET /orchestrations/:id`, `POST /memory/:id/reindex` (re-embed a memory run's lessons), `DELETE /memory/:id` (retract every point a digest run stored), `DELETE /memory/:id/points/:ref` (retract one stored memory by the run it was digested from and its ref, answering what it held), `POST /memory/retrieval-report` (what a recall would find for a goal), `POST /memory/form-retrieval-report` (what a form page's recall would find per field, under the unit of work the body names), `GET /memory/effectiveness` (whether a recalled lesson's run saw its defects resolve), `GET /memory/gaps` (what no recall could serve, by brief), `POST /router/report` (which judge the router would pick). Every wire type is in `@sysdesign/contracts` under `lib/quality-loop`. The web client is `packages/quality-loop-ui` (`pnpm quality:start`).
